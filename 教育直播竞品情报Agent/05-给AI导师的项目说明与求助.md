# 教育直播竞品情报 Agent：项目现状与求助说明

老师您好，我正在做一个“教育直播竞品情报与话术优化 Agent”，内部名称是“直播竞品情报主管”。希望向您说明业务目标、整体方案、实际进展和当前困难，请您帮我判断下一步的重点。

本文依据截至2026年8月28日晚的项目材料、最新运行审计及相关代码整理。文中的目标方案不代表全部实现，局部测试通过也不代表整套系统已经可用。

## 一、我为什么要做这个 Agent

我的需求是围绕低价教育课包，持续研究带同款商品的同行，了解他们如何吸引家长、建立需求和信任、承接商品并推动成交，再用于改进我自己的原创直播内容。

如果靠人工完成，需要不断查同行、盯开播、录制、整理逐字稿、比较前后变化，再判断哪些值得借鉴。这些工作重复、耗时，而且单看一场很难区分稳定打法、临时测试和随机答疑。

因此，我希望把信息采集和整理交给系统，把精力放在业务判断和实际测试上。最终价值不是保存更多录像或生成更多报告，而是持续回答：同行变了什么、证据在哪里、哪些方法适合我、我应该怎样调整。

## 二、输入、输出与能力边界

核心输入是我通过飞书发送的一个5元教育课包商品链接；系统依赖已登录且有相应权限的巨量百应、同行直播入口和我自己的正式话术知识库。

预期输出包括：同行清单、商品与同行关系、直播场次、带时间戳逐字稿、单场分析、最近两场比较、打法版本、策略候选，以及可以人工审核的话术修改建议。

系统只研究当前账号有权查看的信息，登录、验证码及权限异常由人工处理。竞品原话、模型推断和我的正式知识必须分开；未经我明确批准，不能自动修改正式话术。

## 三、整体业务流程

**商品接入 → 发现同行 → 持续监控 → 录制转录 → 跨场研究 → 优化建议 → 人工审核 → 正式话术迭代。**

1. **接收商品并建立任务。** 识别飞书中的商品分享或链接，解析商品身份；重复消息不重复建任务，中断后恢复原任务。
2. **扫描并维护同行集合。** 在巨量百应确认商品、直播记录范围和筛选状态，遍历全部可见结果。用稳定账号ID识别同行，分开维护账号身份与商品关系，不能只按昵称去重。
3. **持续扫描与监控并行。** 周期性发现新增同行，同时检查已有账号是否开播。某轮扫描失败不应中断已有监控；检测失败必须标为“未知”，不能当成“未开播”。
4. **开播后录制、下播后整理。** 同一次真实直播只建一个场次，断流恢复仍归原场次。确认结束后整理整场媒体、提取音频、转录并保存时间戳与缺口信息。
5. **按完整性开展研究。** 部分录制只做有证据的辅助分析；首个完整场建立基线，此后比较最新完整场与上一完整场。分别分析开场、干货、需求、信任、商品承接、成交、答疑等模块，避免整体相似度掩盖关键变化。
6. **形成策略与话术建议。** 追踪变化是否持续出现，把候选策略与我的知识库比较，展示“原内容→建议内容”、来源、理由和风险。我确认值得测试并批准修改后，系统再保存新版本，保留旧版本及依据。

以上是完整目标流程，目前只完成了其中部分链路的真实验证。

## 四、目前采用的架构和策略

**技术分工。** 使用 Hermes 独立 Profile 承载这个 Agent，飞书机器人作为入口；当前 Runtime V3 使用 PostgreSQL 保存任务和业务状态，后台 Worker 执行扫描、监控、录制、转录等工作。浏览器采集使用 Tabbit；媒体处理使用录制组件和 FFmpeg；语音识别使用 faster-whisper；已有语义分析代码调用 DeepSeek。

**执行与判断分开。** 消息受理、状态查询、去重、重试和恢复尽量由确定性程序处理，大模型负责内容理解和分析。通过 Inbox、Checkpoint、Outbox 分别记录消息、执行断点和待交付结果，避免“回复说接到了，但没有任务”，或交付失败后全部重做。

**数据按用途分层。** 当前运行状态以数据库为依据，飞书承担业务查看、结果交付和审核入口；原方案把 Obsidian 作为长文本与正式知识底座，大型音视频留在本地外置存储。后续知识库链路仍需验收，不能视为已经全部接通。

**研究优先看证据。** 每条重要判断应能回到具体同行、场次和时间戳。原设计要求同一同行连续3个真实完整场支持，才确认稳定策略或正式打法版本；这只是稳定性判断规则，不能证明它提高了成交效果，是否适合我还要实际测试。

**成本与风险控制。** 当前配置采用最低可用清晰度和整场录制，视频保留72小时、音频168小时。原业务方案还要求保护最近完整场和关键证据，两套保留规则如何衔接，需要进一步统一并验证。正式知识始终保留人工审批。

## 五、目前实际做到哪一步

已有岗位卡、工作流、流程图和 Profile，并已实现运行代码，不再只是方案设计。

最近的真实修复与验收记录表明：

- 飞书商品分享可以进入任务系统；“继续”和状态查询可以定位原任务。原始消息重复回放100次，没有增加业务任务。
- 两个商品已分别完成扫描，取得55条记录、20个核验同行，以及80条记录、21个核验同行。记录条数不等于账号数量，别名需要归并到稳定身份。
- 商品、同行、商品关系和监控四张飞书表已回读验证，完成通知也已确认送达。
- 已有真实录制文件在持续增长，说明部分录制确实启动成功。
- 最近58项回归测试通过，但未覆盖本次审计发现的所有录制故障。

**当前准确定位是：商品扫描、身份核验、保存和飞书交付已有真实成功闭环；整场录制收尾、完整转录、跨场策略研究及审批更新尚未形成完整业务闭环。**

## 六、当前主要困难和问题

### 1. 下播检测错误，堵住后续处理

主监控探针在未提供时长时，把 `None` 当作时长参数传给录制器，导致参数报错，外层却只显示“未知”。系统要求确认下播后才能结束场次，因此这个错误会让场次长期等待，无法正常收尾。

最近审计时，41个监控目标中36个为未知、5个为直播中，20个场次停在等待直播流状态。这个分布不能直接解释为所有账号都异常，但主探针参数错误已被实际确认。

### 2. 录制状态与实际产物不一致

一个场次只有空输出目录，没有录像。Worker认为没有媒体文件就不需要续录参数，录制器却认为目录已存在就必须续录，两者规则冲突，导致反复重启，累计已超过500次。

这暴露出的问题是：启动了进程不等于开始了有效录制。系统需要以媒体生成和文件增长确认成功，并对失败设置退避及人工介入条件。

### 3. 样本成功不能代表整场转录成功

最近审计中，V3正式整场转录成功数仍为0。现有5条完成转录记录中，2条是5分钟自动样本，3条是历史导入，不能证明新整场链路已经跑通。

此外，代码只要发现同场已有任意完成转录就可能跳过后续处理，5分钟样本存在挡住整场转录的风险。需要明确区分样本、分段、整场和覆盖范围。

### 4. 分析覆盖与业务准确性还不够

当前分析代码只向模型提供逐字稿前16000个字符，长直播的后半段可能没被分析。如果商品承接和成交发生在后面，报告就可能遗漏最重要的内容。

ASR的人工标准答案和时间戳复核也尚未完成。短样本已暴露术语识别质量问题，不能把模型输出直接当作可靠证据。下一步需要解决整场覆盖、模块切分、跨场对齐，以及事实和推断的区分。

### 5. 数据完整性和运行规模仍需验证

同一商品两次复扫都是80条、21个稳定账号，但逐条比较出现1增1减。可能是平台更新，也可能与排序变化有关；由于未保存每条平台直播记录的稳定ID，现有证据不足以确定原因。总数一致不能代替明细一致。

此外，还有20条历史待核实身份占位，不能按名字直接合并。30路常态、50路极限仍是容量目标，短时并发测试不足以证明长期稳定运行。真实素材到期清理也尚未验收。

### 6. 方案、记忆和实现存在不同步

旧基线里“不能自动接单、不能写飞书”等问题已经部分解决，部分长期记忆仍保留旧操作规则。业务文档与最新数据库、媒体保留策略也有差异，容易让 Agent 按过期说明行动。

我需要建立清晰的当前版本和验收依据，避免把“写了规则”“写了代码”“测试通过”“真实业务成功”混为一谈。

## 七、希望您重点帮我判断什么

1. **范围是否过大？** 从同行发现一直做到正式话术更新，是否应该先收敛到“一个商品、一个同行、一场完整直播、一份可信分析”的最小闭环？
2. **架构分工是否合理？** 哪些应由固定程序和状态机完成，哪些才需要 Agent 或大模型？现有 Runtime 是否需要简化，而不是继续增加模块？
3. **如何设计有效的验收？** 怎样验证真实下播、录制完整、整场转录、分析覆盖、故障恢复和飞书交付，避免用样本或进程状态代替成功？
4. **如何做有业务价值的跨场研究？** 连续3场规则是否合理？如何识别结构变化、临时测试与随机表达，并评价建议是否值得我实际采用？
5. **下一步优先顺序怎么排？** 我的初步想法是：先修复监控和录制收尾，再完成一个真实整场的转录与分析验收，然后验证跨场比较和一次真实人工审批，最后扩展并发、长期运行和素材清理。

我最希望得到的帮助，是确定一个范围清楚、可以验收的下一阶段目标，把已经局部跑通的系统，逐步变成能稳定交付、证据可信、真正帮助我改进直播的工具。
