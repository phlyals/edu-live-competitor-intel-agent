# 第八部分：血缘与重算闭环——修复与验证

## 结论

本项已完成生产部署并通过验证。

- `lineage_edges.upstream_version` 现在只把上游文件内容 SHA-256 作为可自动处理的版本身份。
- 每条可验证血缘同时保存上游转录引擎/模型、下游模型、prompt 和分析 schema 版本。
- 历史无法证明来源的边明确标记为 `LEGACY_UNVERIFIED`，不会自动触发模型重算。
- 转录内容、分析 spec、模型或 prompt 任一变化时，只创建一个版本绑定的 `recompute_request`。
- 旧报告文件和 `status=COMPLETE` 保留，但血缘标记为 `STALE`，并创建人工复核项和飞书纠正投影；不会继续伪装成当前决策版本。
- 新分析先以 `PENDING_RECOMPUTE / CANDIDATE` 运行。模型完成后仍不替换旧版本；只有 Evidence 严格验证通过，才在同一数据库事务中把候选切为 CURRENT、旧版本切为 SUPERSEDED、完成重算请求并释放投影。
- 候选失败或证据失败时，旧报告仍可读取且保持 STALE/REVIEW，不会静默丢失或错误恢复为 CURRENT。

## 根因

旧 `v3_recompute_worker.py` 只扫描已经人为标成 `STALE` 的 edge，然后把 analysis 状态改成 STALE 并插入一个固定 review ID。它不会发现转录文件内容变化，不会比较模型/prompt/spec，不会创建新 analysis，也不会等待新证据完成后切换版本。固定 review 唯一键还会吞掉同一分析后续版本的复核事项。

部分历史 edge 的 `upstream_version` 实际是路径或其他对象哈希，不能证明绑定的是哪份 transcript 内容。直接拿这些 edge 自动重算会把不可信历史继续传播。

## 修复内容

### 1. 血缘身份

- 为 `lineage_edges` 增加 `binding_status` 和五类引擎/模型/prompt/schema 版本字段。
- migration 004 只把满足以下条件的旧 edge 标为 `CONTENT_DIGEST_VERIFIED`：
  - downstream analysis 明确绑定同一个 transcript ID；
  - edge upstream version 与 analysis 的 transcript content digest 完全相同；
  - digest 是 64 位 SHA-256。
- 其他旧 edge 标为 `LEGACY_UNVERIFIED`，保留原状态和原值。
- PostgreSQL trigger 禁止事后修改 edge 身份与版本字段，只允许状态、时间和审计 metadata 演进。

### 2. 持久重算请求

- 新增 `recompute_requests` 表，唯一身份包含：旧 analysis、transcript、旧/新内容 digest、目标 spec/model/prompt。
- 请求支持原子 claim、lease、lease epoch、attempt、checkpoint 和失败重试。
- 同一版本变化被多次发现或并发发现时，只产生一行。
- request 身份由 PostgreSQL trigger 保护，创建后不能改成另一份上游或另一套模型配置。

### 3. 发现与执行

- Pipeline 每轮对合格 FULL_SESSION transcript 重新计算实际文件 SHA，而不是依赖路径或旧 metadata。
- 没有旧正式分析时仍按原逻辑创建首个分析，ID 算法保持向后兼容。
- 有旧正式分析且目标身份变化时，Pipeline 创建 recompute request、标记旧结果 STALE、创建带版本的 review，并投递 STALE 纠正信息。
- Recompute worker 领取请求后再次读取并校验当前 transcript SHA；若内容再次变化，旧请求标为 OBSOLETE，由新 digest 生成新请求。
- Recompute worker 创建确定 ID 的 `PENDING_RECOMPUTE / CANDIDATE` analysis 和 `CANDIDATE` edge；崩溃重试不会复制候选。

### 4. 证据后切换

- Analysis worker 对候选额外核验 request ID、候选 ID、transcript ID、digest、spec/model/prompt 和 CANDIDATE edge。
- Analysis 完成后只生成候选 artifact、REQUIRED evidence 和 HELD_EVIDENCE outbox，不提前替换旧报告。
- Evidence worker同时核验 content digest、引擎/模型/prompt/schema 版本以及原 source segment 绑定。
- Evidence VERIFIED 后，同一事务完成：候选 CURRENT、旧版 SUPERSEDED、两侧 edge 状态切换、request COMPLETE、review RESOLVED、旧版纠正投影入队、候选投影释放。

### 真实 PostgreSQL

两套 Python 环境串行各执行 13 项，全部通过。其中本项新增 5 项：

- 8 个并发请求写入收敛为一条 recompute request。
- recompute claim 同一时刻只有一个 owner；过期 epoch 无法保存断点，新 epoch 可接管。
- request 身份字段不可修改。
- lineage digest/版本身份不可修改，但 state 可正常演进。
- 生产克隆中的 legacy edge 不会产生自动重算请求。

并行使用同一个破坏性测试库会互相清表，因此最终证据采用两套环境串行运行；早先并行干扰日志未被计为通过证据。

### 故障与状态机

- transcript 内容变化：只创建一个请求，重复扫描为 0。
- spec、model、prompt 各自变化：分别创建且只创建一个请求。
- transcript 在请求处理中再次变化：旧请求 OBSOLETE，新请求保持 PENDING。
- 模型候选失败：request FAILED_FINAL；旧 artifact 仍存在，旧 analysis 保持 COMPLETE/STALE，review 保持 PENDING。
- 候选模型成功但证据未验证：候选 COMPLETE/CANDIDATE，旧版 COMPLETE/STALE，没有 CURRENT 偷跑。
- 证据通过：候选 CURRENT、旧版 SUPERSEDED、request COMPLETE、review RESOLVED、held outbox 全部释放。

## 已知边界

- `LEGACY_UNVERIFIED` 历史边无法自动恢复真实来源，只能保留并等待人工证据修复；本次没有伪造回填。
