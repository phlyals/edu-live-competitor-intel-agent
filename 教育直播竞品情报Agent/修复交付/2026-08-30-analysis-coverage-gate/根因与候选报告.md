# P1-8 分析覆盖率门禁：根因与隔离候选报告

## 范围与安全边界

- 本次只审计生产数据并在 `staging/` 构造候选，没有修改生产代码、数据库、服务或媒体。
- PostgreSQL 审计事务显式为 `transaction_read_only=on`。
- 没有调用模型 API；既有分析产物的验证均为内存重算，没有写回原文件。
- 原验收脚本未修改。

## 根因

生产 `v3_analysis_worker.py` 有四条可虚报路径：

1. `timeline_coverage_rate` 使用 `最后时间戳 - 第一时间戳`。中间无转录/未分析的缺口也被算成已覆盖。
2. `segment_coverage_rate` 无条件写死为 `1.0`，没有任何成功处理的 source segment ID 证据。
3. 分析成功后无覆盖率门禁，始终把 `analyses.status` 更新为 `COMPLETE` 并投递正式飞书投影。
4. 待处理分析按 `session_id` 连接任意 `COMPLETE` 转录；同一场存在样本和完整场时，不能证明分析使用的是创建任务时绑定的那份转录。

生产只读证据：

- 当前唯一 Runtime V3 正式完整场分析存储值为 `0.9997060866`，真实时间戳并集 / 实际音频时长为 `0.9880816582`。
- 3787 秒模拟场存储值为 `0.9987946794`，真实并集率为 `0.9813988502`。
- 两者修正后仍超过 0.95，因此候选不会误伤这两份合格完整场。
- 生产另有两份 `sample_only=true` 的分析仍标为 `COMPLETE`；它们由 P1-7 样本范围修复负责迁移，P1-8 候选同时 fail-closed，样本范围无法成为正式分析。

详细证据：

- `证据/生产分析覆盖率只读审计-转录门禁上线后.json`
- `证据/候选对既有完整产物的只读重算.json`

## 最小候选

候选文件：

- `staging/runtime/v3/v3_analysis_worker.py`
- `staging/runtime/v3/test_v3_analysis_worker.py`
- `staging/runtime/v3/v3_config.json`
- 汇总补丁 `analysis-coverage-gate.patch`

核心行为：

1. 从原始 `FULL_SESSION` transcript 的 `segments` 建立稳定 ID：`{transcript_id}:segment:{原始数组序号}`。
2. 每个模型 chunk 记录实际成功处理的 `source_segment_ids` 及 SHA-256。
3. 用成功 ID 对应时间戳的区间并集除以 P1-6 记录的真实音频时长，计算 `analysis_coverage_rate`；缺口单独输出。
4. `segment_coverage_rate` 由成功唯一 ID 数 / 原始 source segment 数计算，不再写死。
5. 最低正式门槛为 0.90，目标为 0.95：
   - `<0.90` 或时间戳/ID/chunk/范围任一无效：`QUALITY_BLOCKED`，不能 `COMPLETE`，不能生成新的正式投影。
   - `0.90 <= rate < 0.95`：可标记最低门槛合格，但明确 `meets_target=false`。
   - `>=0.95`：`QUALIFIED_TARGET`。
6. 分析只通过 `lineage_edges.upstream_version = analyses.source_digest` 绑定创建任务时的精确 transcript，不再按 session 任取一份。
7. 与 P1-6 兼容：若 transcript 已有 `timestamp_coverage`，候选重新计算并要求时长、并集率、`timestamps_valid` 和 `is_qualified` 一致。
8. 与 P1-7 兼容：要求 `coverage_scope=FULL_SESSION` 且 `sample_only != true`；样本在模型调用前即阻断。
9. 旧完整场只有在 source content hash 与每个成功 chunk 诊断都精确匹配时，才允许不调用模型地重算覆盖率；否则 fail-closed，等待重跑。

## Trade-off 与上线注意事项

- 严格策略会阻断含空文本、非法时间戳、重复 ID 或缺失 chunk 诊断的分析。这会增加 `QUALITY_BLOCKED/WAITING_MODEL`，但不会再把不可证明完整的结果冒充正式结果。
- source segment ID 在一份 transcript 内稳定，不跨 transcript 复用；transcript 重排或替换会产生新证据版本，这是期望行为。
- 完整 source ID 列表保存在分析 artifact，文件会增大约几十至一百多 KB；数据库 metadata 只保存计数、比率和 SHA-256，避免控制面膨胀。
- 0.90 到 0.95 之间仍可最低合格，但必须对外显示“未达到目标”；如果业务希望 0.95 才允许正式投影，只需把 minimum 配为 0.95，不改算法。
- 集成时不要用候选 `v3_config.json` 覆盖后来新增的配置；只合并 `analysis_quality` 块。当前候选已包含 P1-6 的 `transcript_quality`，但 P1-7 若继续新增配置，仍应按块合并。

## 结论

根因已定位，隔离候选和完整回归均通过。尚未部署生产；应在 P1-7 样本范围修复合并后，将此候选按当前生产代码做三方合并，再重载 analysis-v3 并只读核验心跳、完整场重验证和飞书投影状态。
