# 飞书控制路由与真实扫描超时修复报告

日期：2026-09-01

## 用户看到的实际问题

飞书新文案已生效，但用户回复“继续第一个”后，消息没有进入 Runtime V3 任务控制，而是进入普通聊天 Agent。普通 Agent 从旧会话中恢复了已经取消的 ASR 人工复核，随后发送了长篇技术说明、SQL 审批卡和 self-improvement 提示。这些内容与当前商品任务无关。

用户之后回复“确认”时，同样被普通聊天 Agent 误接收，进一步放大了无关内容。

## 根因

1. 控制语法只识别“继续处理”或内部任务编号，不识别“继续第一个/第二个”。
2. 多商品列表按旧任务顺序展示，最近发送的商品没有排在第一位。
3. “巨量百应已登录，你看一下”和“确认”未被确定性控制器识别，会落入普通聊天 Agent。
4. 普通聊天会话仍保留旧 ASR 人工复核上下文。
5. 登录恢复后，真实扫描前两页成功，第三页一次处理 12 条详情记录超过 Tabbit 120 秒硬上限；原错误分类又把超时判成需要人工处理。

## 修复

### 飞书控制路由

- 支持“继续第一个/第二个/第三个”、数字序号、商品编号。
- 支持“巨量百应已登录”“精选联盟登录好了”等自然表达，自动选择最近商品。
- 裸“确认”进入确定性状态查询，不再进入普通聊天 Agent 或审批流程。
- 多商品列表按最近活动时间倒序，最近商品排第一。
- 列表只显示序号和商品编号，不显示内部 `task_...`。

### 旧会话与 ASR 待办

- 导出并删除会话 `20260901_175523_5edc00fb`，清空该飞书 DM 的旧会话索引。
- 将过期的 ASR 人工复核 `review_62fe3cd307db300b3310b7ba` 标记为 `CANCELLED`。
- 取消原因明确记录为：用户此前已经决定当前场景不需要人工金标或逐段时间戳确认；没有把 ASR 错误标记为生产就绪。

### 扫描超时

- 保留 Tabbit 120 秒硬上限。
- 将每页 12 条详情拆为每批 4 条；每批保存 `rowOffset` 和采集证据。
- 一页完成后再翻页，保证不会漏行、重复行或提前判定末页。
- controller timeout 归类为可自动重试的页面临时问题，不再要求用户重复回复。

### 网关提示

- 配置 `feishu.gateway_restart_notification=false`，后续运维重载不再向业务聊天发送英文 Gateway shutdown 提示。
