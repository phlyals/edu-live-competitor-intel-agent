## 审计结论

生产 `v3_analysis_worker.py` 当前存在两条会制造“看似有证据”的路径：

1. `request_chunk()` 要求模型自由返回 `{summary,start,end}`。校验只确认时间落在 chunk 首尾之间，不能证明这段时间真的对应某条原始逐字稿。
2. `merge_chunk_results()` 先找与自由时间段重叠的逐字稿；如果没有重叠，就把整场所有逐字稿作为候选，再选开始时间最近的一行。这就是 nearest-line fallback。模型即使给出一个没有证据的时间，也会被程序强行贴到某句真实原文上。

只读审计发现现有 3 个 Runtime V3 JSON 分析产物全部为 `LEGACY_UNBOUND`：一个 schema 2.0，两个无 schema。它们仍可读取，但不能证明时间引用来自模型实际看到的原始 segment。

## 候选修法

### 1. 给原始 transcript segment 派生稳定 ID

候选 `v3_analysis_worker.py:57` 的 `bind_transcript_segments()` 对每条原始 segment 生成：

- `source_segment_id`
- 原始 `start/end`
- 原始 `source_text`
- `content_digest = SHA256(source_text)`

ID 由绝对 segment index、原始 start/end、原文 digest 确定，与 chunk 大小无关，也不受 `normalized_text` 变化影响。原文或原始时间被改动时，ID 会有意变化，防止把旧证据套到新内容上。

### 2. 模型只能看和返回 ID

候选 `v3_analysis_worker.py:103-169,234-277`：

- 输入格式改成 `[source_segment_id] 文本`，不再把时间戳发给模型。
- 输出 item 只能是 `{summary,source_segment_ids}`。
- Prompt 明确禁止生成、猜测或输出时间戳。
- 旧式 `{summary,start,end}`、字段缺失、额外字段都视为无效响应并重试。

### 3. 严格校验并由程序回填原始证据

候选 `v3_analysis_worker.py:172-231`：

- 每个 ID 必须属于**当前 chunk**。
- 伪造 ID、另一 chunk 的真实 ID、重复 ID 均 fail closed。
- 校验通过后，程序从当前 chunk 本地映射回填每条引用的原始 start/end/source_text/content_digest。
- 保留顶层 start/end 仅供旧消费者排序兼容；正式证据是 `source_segments[]` 和模块中的逐条精确 timestamps，不使用兼容区间做证据判断。

### 4. 删除 nearest-line fallback

候选 `v3_analysis_worker.py:280-345`：

- 模块时间戳直接复制模型引用的原始 segment 证据。
- 没有“无重叠时选最近一句”的路径。
- 输出升级为 schema 3.0，并显式记录 `nearest_segment_fallback=false`、`model_generated_timestamps=false`。

### 5. 保存 ID 与 digest 证据清单

候选 `v3_analysis_worker.py:348-422,449-486`：

- 分析 artifact 增加 `evidence`，保存 transcript artifact SHA256、所有引用 ID、每条 content digest，以及引用集合 digest。
- analyses metadata 和 evidence bundle metadata 保存 binding 状态与摘要。
- 写文件后仍由现有 evidence worker 校验整个 artifact 哈希；即使 evidence bundle 后续压缩 metadata，immutable artifact 内仍保留完整引用清单。

## 旧 JSON 与迁移策略

- 新模型若偶尔返回旧 `{start,end}` 格式：拒绝、带纠错提示重试；3 次失败后保持 `WAITING_MODEL`，不做最近行映射。
- 旧 artifact：继续可读，`artifact_binding_status()` 标成 `LEGACY_UNBOUND`，不能自动升级为可信证据。
- 正式迁移：只对仍应作为正式结果的 current/full-session 分析重新运行 schema 3；历史/样本结果保留原文件和哈希，但不得标成 `BOUND_V1`。
- **禁止的迁移方式**：根据旧 start/end 找最近 segment 后直接回填。这会延续当前缺陷。

## Trade-off

1. ID 比旧时间前缀更长，真实样本从旧格式约较少字符增长到 78394 字符、16 个 chunk，API 调用数、成本和总耗时会上升。
2. 严格 JSON/ID 校验可能让尚未适应新 schema 的模型多重试，极端情况下停在 `WAITING_MODEL`；这是有意的 fail closed。
3. 已有 schema 2 产物不会自动变可信。需要重新分析才可获得 `BOUND_V1`，会增加一次模型成本；旧文件本身不删除、不覆写。
4. 证据绑定证明“摘要引用了哪几句原文”，不等于自动证明摘要语义一定正确。后续仍需抽样、人审或 entailment 检查。
5. 一个结论可引用最多 3 条 segment。为兼容旧消费者保留的顶层 start/end 是这些引用的时间包络；任何正式证据展示与校验必须使用 `source_segments[]` 中的逐条原始区间。
