# 第七部分：长任务原子领取、租约、断点与重试——修复与验证

## 结论

本项已完成生产部署并通过验证。

- 转录和分析任务在 PostgreSQL 中以单条原子语句领取；并发 worker 不会领取同一个任务。
- 每次领取都有独立 `lease_epoch`。旧进程、已超时进程以及被新进程接管的进程都不能更新断点、重试状态或最终结果。
- ASR 子进程运行期间每 15 秒续租并刷新 Pipeline 心跳。
- 分析每完成一个 chunk 就原子保存结果文件、文件哈希和数据库断点；进程退出后只重做未完成 chunk。
- 转录和分析最终文件都包含 lease epoch 与 attempt，不覆盖旧尝试文件；只有带有效租约的数据库 CAS 成功后，文件才成为正式结果。
- 401/403/明确 4xx 直接进入最终失败；timeout、连接错误、408、429、5xx、不完整 JSON、异常 finish reason 和模型结构错误执行有界重试。
- 生产迁移后没有自动重跑旧任务：可执行长任务为 0，原有 COMPLETE/历史状态全部保留。

## 根因

旧 Pipeline 和 Analysis 只是查询待处理行后直接工作，没有数据库原子 claim、owner、租约或 fencing token。两个进程可能处理同一对象；旧进程即使已经超时，仍能覆盖新进程的状态。分析 chunk 只存在内存里，某一 chunk 失败后整场需要从头重跑。HTTP 请求也没有完整区分限流、服务端失败、鉴权失败、截断 JSON 和模型结构错误。

审查候选实现时还发现两个边界问题，并在部署前修复：

1. 转录失败处理可能用“领取任务时的旧断点”覆盖刚保存的音频断点。
2. 旧进程租约已经超时、但尚未被新进程领取时，仍可能提交结果。

现在失败路径保留最新内存/数据库断点；所有续租、断点、重试和完成操作同时校验 owner、epoch 和 `lease_until > 当前时间`。

## 生产变更

- 新增 `v3_long_jobs.py`：统一实现 PostgreSQL `FOR UPDATE SKIP LOCKED` 原子领取、续租、断点、完成、失败重试和过期任务收敛。
- 修改 `v3_pipeline_worker.py`：先创建持久任务，再领取；ASR 子进程续租；音频和转录产物按尝试版本化；失败保留最新断点。
- 修改 `v3_analysis_worker.py`：分块断点、模型/API 错误分类、指数退避、租约续期、版本化结果和 fenced 发布。
- 新增 migration 003，为 `transcripts`、`analyses` 增加 attempts、next attempt、owner、lease、epoch、error 和 checkpoint 字段及到期索引。
- 新增带计划哈希、完整行备份、健康后置条件的迁移脚本，以及仅在租约从未使用时允许执行的安全回滚脚本。
- 未修改录制模块、原验收脚本、转录内容或既有分析产物。

## 验证结果

### 1. 完整代码回归

### 2. 真实 PostgreSQL 并发与故障注入

两套 Python 环境各执行 8 项，全部通过：

- 8 个 worker 并发领取 40 个任务，每个任务恰好一个 epoch。
- 两个 worker 同时领取单个分析任务，只有一个成功。
- 两个 worker 同时领取单个转录任务，只有一个成功。
- 过期任务被新 owner 接管后，旧 epoch 无法保存断点。
- 租约仅仅过期、尚未被接管时，旧 owner 同样无法提交。
- `RUNNING` 但 lease 为空的孤儿任务可恢复领取。
- 最后一次尝试过期后收敛为 `FAILED_FINAL`。

### 3. 分析重试与断点

- 429 后成功、503 后成功、连接错误、读取超时、截断 JSON、异常 finish reason、模型 schema 错误：按策略重试并成功。
- 401、403、400、内容安全阻断：不重试。
- 第 N 个 chunk 失败后，已完成 chunk 的 JSON、哈希及 source segment 集合校验通过；下一次只请求剩余 chunk。
- 被接管的旧分析进程即使写出了孤立版本文件，也不能写入 analyses、evidence 或 outbox。
- ASR 失败后数据库仍保留 `AUDIO_READY` 断点，不再倒退成旧断点。

## 已知边界

- 外部模型超时发生在服务端已经完成、但客户端未收到响应时，下一次尝试仍可能产生重复费用；fencing 能阻止重复正式提交，不能让第三方 API 实现绝对 exactly-once。
- 进程失去租约后写出的版本化孤立文件不会成为正式结果，需要后续独立的安全清理策略处理。
- 本次生产没有待处理长任务，因此没有为了验证而人工制造生产 ASR/模型任务；生产行为由隔离 PostgreSQL、故障注入和既有正式产物的原验收共同验证，下一场自然任务会继续留下真实运行证据。
