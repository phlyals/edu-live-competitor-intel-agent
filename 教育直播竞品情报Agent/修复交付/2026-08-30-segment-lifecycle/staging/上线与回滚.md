# 上线、trade-off 与回滚要求

## 维护窗口顺序

1. 确认没有活跃 recorder；暂停 pipeline 和 finalizer/runtime 的收尾入口，不停止独立 recorder。
2. 用 `pg_dump -Fc` 备份生产库，文件权限 0600；用 `pg_restore --list` 验证备份可读，并把 SHA-256 写入独立记录。
3. 在显式 READ ONLY 事务运行 migration dry-run，保存 `plan_sha256` 和逐类计数。
4. 人工核对：canonical、superseded、retained/lost、待取消 transcript 数量；任何未知项都停止上线。
5. 用相同快照口径和 `--expected-plan-sha256` 执行 apply。apply 强制 `--full-media-hash`，若媒体或计划变化会失败，不会部分提交。
6. 安装候选补丁。先启动 finalizer/runtime，确认新产出的 canonical lifecycle；再启动 pipeline。
7. 验证 pipeline 查询只命中 `CANONICAL_ACTIVE`，旧分段和已取消 transcript 不再被重复消费。

## Trade-off

- `UNCLASSIFIED` 是 fail-closed 默认值。DDL 已加但历史分类未完成时，旧数据不会进入转录；因此 DDL、数据迁移和代码切换必须在同一维护窗口完成。
- `SOURCE_SUPERSEDED` 只表示旧源路径退出处理，并不表示整场录像完整；完整性仍由 media coverage/验收链单独判断。
- apply 必须重算 canonical 大媒体 SHA-256，会造成明显顺序读 I/O，并可能持续较久；应避开录制高峰，不允许为了速度关闭该门禁。
- 245条历史 `WAITING_TOOL` 改为取消后不会自动重试；行、原 metadata 和取消原因仍保留。如需重做，应从 canonical 创建新 transcript，不复活失效路径。
- 两条仍存在但没有 verified canonical 的历史来源只会进入 `SOURCE_RETAINED`/人工复核，不会被当作整场主媒体。
- finalizer 搬移 retained source 时会更新路径；若目标路径已有同哈希 owner，保留 owner、淘汰旧重复行。哈希冲突进入 `LOST_REVIEW`，不会覆盖文件或行。
- 新增自引用外键阻止 canonical 被删除时遗留悬空 superseded 引用；这也意味着未来删除 segment 必须先处理引用。

## 回滚

### 紧急应用回滚

1. 暂停 pipeline/finalizer；不要停止正在写媒体的 recorder。
2. 回滚 `v3_pipeline_worker.py`、`v3_worker.py`、`v3_runtime.py` 和 schema 初始化代码。
3. 新增列和索引可暂时保留；旧代码会忽略它们，紧急情况下不要做 `DROP COLUMN`。
4. 若数据迁移已提交，从0600备份在克隆库恢复并核对；再按 `segment_id`/`transcript_id` 定向恢复原 lifecycle、transcript status 和 metadata。禁止不经核对直接覆盖整个生产库。
5. 验证 recording/transcription/analysis 行数、媒体清单和服务心跳后再恢复 worker。

### 后续物理回滚

只有所有使用新列的代码都已撤回，才能在单独维护窗口删除索引、外键和三列。物理回滚会丢失生命周期审计信息，默认不建议执行。
