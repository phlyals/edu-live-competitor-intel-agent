## 一、当前代码事实

当前 [`v3_worker.py`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_worker.py:454) 的 finalizer：

1. 在第 473 行按文件 `mtime` 排序，文件名只作为并列时的稳定排序键。
2. 第 483 行以单个 FFmpeg stream-copy concat 生成临时 TS。
3. 第 487 行发布最终 TS 后，第 488～490 行立即删除所有源分段。
4. 第 513～516 行只验证最终容器可读取且 duration 大于零。
5. 第 527 行 manifest 只保存最终文件，不保存源分段顺序、大小、时长、A/V、sidecar 状态或退出信息。

因此，最终文件一旦生成，系统很快就失去独立复核和重新合并所需的源文件。

## 五、最终 TS 与源证据抽样

抽查 6 个近期多分段最终 TS：

- 6 / 6 FFprobe 返回成功；
- 6 / 6 最终文件同时包含 H.264 视频和 AAC 音频；
- 所有对应源媒体均已删除，源 A/V 无法重新探测；
- 四个样本的最终 duration 与 sidecar 活跃墙钟累计相差约 -6.3～+9.9 秒；
- 另两个样本分别少约 143 秒和 163 秒。

sidecar 墙钟时间可能包含断流、等待和尾部无媒体时间，因此 143/163 秒差异**不能单独证明最终 TS 丢包**。它证明的是：源文件已经删除后，现有证据不足以分辨“真实媒体较短”与“拼接漏段”。

这组数据可作为第五项修复后的自然验收候选，但不能提前冒充“最终文件与源文件一致”。

## 六、建议的最小修复边界

只修 finalizer 的可恢复性和基本证据，不扩展成实时转码或双 FFmpeg 架构：

1. **确定顺序**
   - 新格式 `整场直播.ts.partial`、`refreshNNNN` 按 generation 0、1、2……排序。
   - generation 重复、缺失或无法解析时 fail-closed，不合并、不删除。
   - 仅旧式无法解析的历史文件允许回退 mtime，并在 manifest 标记 `LEGACY_MTIME`。

2. **合并前写精简 source manifest**
   - 每段记录：generation、实际相对路径、bytes、FFprobe duration、是否有 audio/video、codec、对应 sidecar 的状态和 return code。
   - 不保存原始 URL、token、query 值或完整 stderr。
   - 第一版不必增加数据库 schema；先写入场次目录的原子 JSON 文件即可。

3. **只做元数据校验**
   - 源段及最终 TS 的 FFprobe 均需成功；
   - 每段及最终文件需同时有音频和视频；
   - 最终 duration 与源段 FFprobe duration 之和应在预设容差内；
   - 不新增全包解码、实时转码或第二路录制 FFmpeg。

4. **停止立即删除**
   - 多分段合并成功后，源分段和 sidecar 留在同一 completed 场次目录至少 24 小时；
   - 单分段仍可 rename 成最终文件，无额外空间；
   - 24 小时后的删除交给独立 retention 规则，不能在 finalizer 内 `unlink()`；当前 retention kill switch 仍关闭，因此源文件会安全保留，直到删除规则另行验证。

5. **保持原子发布**
   - 继续使用 `.merge.tmp`，所有校验通过后才 `replace()` 为最终 TS；
   - 任一步失败时保留全部源文件、临时结果和简短错误证据，场次不提升为 `MEDIA_COMPLETE`。

## 七、最小验证集

1. 三个短分段，故意反向修改 mtime：确认仍按 generation 合并。
2. generation 缺号或重复：确认 fail-closed，源文件一个不少。
3. 某段只有音频、只有视频或 FFprobe 失败：确认不发布最终文件。
4. concat 返回非零或最终 duration 超出容差：确认不删源、不写 VERIFIED manifest。
5. 正常三段：确认最终文件 A/V、duration 和 source manifest 合格，源文件仍在。
6. 模拟在 manifest、concat、replace、数据库提交各步骤中断：重启后不得覆盖已验证结果，不得删除唯一源。
7. 部署后选一场自然结束的真实多分段直播，24小时内复核所有源文件、sidecar、source manifest、最终 TS；人工播放头、中、尾和至少两个刷新交界点。

## 八、结论

第五项应优先修“立即删除源分段”，同时加 generation 排序和轻量 FFprobe 证据。当前没有必要引入全包实时转码、重编码或双 FFmpeg 录制。以最近24小时负载计算，源分段保留24小时预计增加约43.758 GiB，当前容量可承受；必须配磁盘阈值监控，并在 retention 规则经过单独验证后再恢复延迟清理。
