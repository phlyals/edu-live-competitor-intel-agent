`当前 CANONICAL_ACTIVE 媒体 checksum → FULL_SESSION transcript source_digest → timestamp coverage ≥ 90% → analyses.transcript_id + transcript content digest + spec/model/prompt version → artifact digest → evidence 三方 hash → qualified outbox/receipt`

## 根因

1. `create_analysis_tasks()` 只要求 transcript 为 `COMPLETE` 且输出为 JSON，没有区分 `SAMPLE` 与 `FULL_SESSION`。
2. 分析 worker 通过 `session_id` 连接 analyses 与 transcripts，而 analyses 表没有不可变的 `transcript_id`，同场存在多个转录时可能读错来源。
3. “同场已有任意 single_session 分析就跳过”的逻辑让旧 SAMPLE 反过来阻止未来完整场分析。
4. transcript、analysis、evidence、outbox/receipt 没有独立的 `scope` 和 `qualification_status`，文件存在、hash 可读会被误当成业务合格。
5. evidence worker 只校验 bundle 文件 hash，没有同时绑定 analysis identity、transcript content digest、唯一 CURRENT lineage 和 artifact 根身份。
6. 飞书 projector 无条件把 Runtime 分析显示为“单场分析/完成”。

## 候选修复

### 数据契约与数据库

`002_analysis_qualification.sql` 新增：

- `transcripts.scope / qualification_status`
- `analyses.transcript_id / scope / qualification_status`
- 不可变身份：`transcript_content_digest / analysis_spec_version / model_version / prompt_version / artifact_digest`
- `evidence_bundles`、`outbox`、`delivery_receipts` 的 scope/qualification
- 完整 immutable identity 唯一索引：transcript + content digest + analysis type + spec + model + prompt
- PostgreSQL trigger：正式/样本 analysis 建立身份后，禁止修改 session、transcript、analysis type、source/content digest、spec/model/prompt；完成后的 output/artifact digest 也不可替换
- 移除旧的 `(session_id, analysis_type, source_digest)` 唯一约束，使新 spec/model/prompt 版本可以形成新分析版本

共享契约集中在 `v3_analysis_contract.py`，避免 pipeline、analysis、evidence 对状态字符串和版本号各自解释。

### Pipeline

只有同时满足以下条件才创建正式分析：

- transcript 列为 `FULL_SESSION / FULL_SESSION_QUALIFIED`
- timestamp 全合法且覆盖率不低于 90%
- session 为 `MEDIA_COMPLETE / COMPLETE` 且连续采集证据为真
- `source_segment_id` 是当前 `CANONICAL_ACTIVE`
- transcript `source_digest == sha256("FULL_SESSION:" + 当前 canonical checksum)`；checksum 缺失时才从现存媒体安全重算
- transcript JSON 文件存在，并计算内容 SHA-256

任务去重使用完整 immutable identity，不再按 session 阻断。SAMPLE 保留为转录诊断材料，但不会创建正式分析。

### Analysis worker

- 直接通过 `analyses.transcript_id` 读取唯一 transcript，不再按 session JOIN。
- 要求唯一 CURRENT lineage 的 `(upstream_id, upstream_version)` 精确等于 `(transcript_id, transcript_content_digest)`。
- 再次校验 canonical checksum 派生 source digest、scope/qualification、timestamp gate、实际 transcript 文件 digest、spec/model/prompt。
- 输出 artifact 写入完整版本身份；成功后保存 artifact digest。
- 只有该 immutable identity 仍未变化时，才可完成 analysis、创建 evidence、进入 outbox。

### Evidence worker

正式 evidence 必须同时满足：

- actual artifact SHA-256 = bundle manifest hash = analyses.artifact digest
- artifact 根 `analysis_id/session_id/transcript_id` 与数据库一致
- 新 artifact 的 content/spec/model/prompt 版本全部一致；迁移前唯一完整分析使用明确的 `LEGACY_ROOT_IDS_PLUS_THREE_WAY_DIGEST` 规则重新验证
- transcript 文件实际 digest 与 analyses 记录一致
- 恰好一条 CURRENT lineage，ID 与 version 均精确匹配

验证成功时合并旧 metadata，不再覆盖并丢失迁移审计字段。

### 历史样本与飞书

不删除历史文件、analysis、bundle、outbox 或 receipt：

- analysis → `SAMPLE_NONQUALIFYING / INVALIDATED / SAMPLE_AUXILIARY`
- 所有样本 lineage edge → `INVALIDATED`
- evidence → `INVALIDATED_SAMPLE`
- 原 outbox/receipt 保留原 `SENT/VERIFIED` 事实，但 scope/qualification 标为样本不合格
- 每条样本新增唯一 `correction_version=1` 投递；projector 把飞书原记录原位更新为“部分场辅助 / 证据不足”，证据说明明确“不代表整场、不可用于正式决策”

## 迁移、幂等和回滚

迁移默认只读。`--apply` 必须提供刚生成的 plan SHA，并使用 SERIALIZABLE 事务、advisory lock、DDL hash 和 source schema signature。写前生成权限 `0600` 的完整行备份。schema marker 最后写入；重复执行只有在列、索引、trigger、所有 backfill、formal/sample lineage、evidence 和 correction outbox/receipt 均无漂移时才返回 `ALREADY_APPLIED`。

可执行 rollback 会核对备份 `0600` 权限、migration key/version、DDL hash 和 PostgreSQL system/database identity，并要求每个 SAMPLE **恰好一条** correction，object 集合完全一致，且 correction 仍为 `PENDING`、`attempts=0`、`last_attempt_at IS NULL`、无 receipt。缺失、重复、漂移或已经尝试投递（包括 RETRY）都会拒绝物理回滚，因为远端可能已成功但响应丢失；此时必须发送新的补偿投影。回滚恢复历史行后也恢复旧代码依赖的 `(session_id, analysis_type, source_digest)` 唯一约束；重新 apply 002 时再移除。

## Trade-off

- 严格 fail closed 会让缺字段、旧 lineage 或 artifact 被替换的分析进入阻断，而不是继续交付；这会增加少量人工复核，但避免样本再次冒充整场。
- 模型版本字段记录当前 API 返回/配置可见的 `deepseek-chat` 标识；供应商内部未公开的底层构建号无法凭空获得。prompt/spec 版本和内容/artifact digest 仍保证本系统侧可复现身份。
- 历史飞书记录不能当作“从未发送”。方案保留 SENT/VERIFIED 事实，并通过 correction 明确撤销其业务资格。
- 新 PostgreSQL 库必须执行 002 才具备 immutable trigger；共享 schema 包含字段和索引，但 SQLite 不承载 PostgreSQL trigger。启动/部署门禁必须检查 migration marker 与 trigger health。
