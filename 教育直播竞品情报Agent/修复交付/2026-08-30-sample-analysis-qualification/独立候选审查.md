## P0：部署前必须解决

### P0-1：迁移没有在 PostgreSQL 克隆环境实际跑过

证据：

- `v3_sample_analysis_migration.py:296` 用一次 `cur.execute()` 执行整份 002 DDL。
- 现有测试只覆盖 helper 和 SQLite 业务函数，没有调用 `apply()`，也没有验证：
  - 多语句 DDL；
  - PL/pgSQL function/trigger；
  - 部分失败时事务是否完整回滚；
  - 唯一索引创建；
  - 第二次执行；
  - 备份恢复。

风险：生产首次发现语法、约束或触发器问题时，pipeline/analysis/evidence/runtime 已经切换，可能造成全链路停摆或数据一半新一半旧。

部署门槛：

1. 在生产克隆库或隔离 schema 执行一次完整 `readonly plan → apply → postcondition → second apply`。
2. 人为注入 postcondition 失败，确认 DDL、数据回填、schema_meta、correction outbox 全部回滚。
3. 用备份做一次恢复演练；仅有 JSON 备份文件而没有可执行恢复步骤，不算回滚方案。

### P0-2：服务切换顺序不完整会让纠正消息再次写错

证据：

- 新 `complete_outbox()` 才会把 outbox 的 `scope/qualification_status` 复制到 receipt（`v3_runtime.py:592-603`）。
- 纠正 outbox 会调用 `v3_project_feishu.py` 中的新映射。
- 生产 runtime-v3 长进程已把旧 `v3_runtime` 函数加载在内存中；仅重载 pipeline/analysis/evidence 不够。
- 迁移会立即创建两条 `PENDING` 纠正 outbox。

风险：

- 若 runtime 出箱没有先暂停，旧 projector 可能在迁移和代码切换之间把样本再次写成“正式完成”。
- 若 projector 已更新但 runtime 未重载，Feishu 内容可能被纠正，但新 receipt 仍落成默认 `UNCLASSIFIED`，证据链不闭合。

必须采用的切换顺序：

1. 暂停 runtime 出箱、pipeline、analysis、evidence；保留 recorder 子进程。
2. 记录 PID、outbox/receipt、媒体与数据库基线，并做 pg_dump + 行级备份。
3. 应用 002 迁移。
4. 原子安装所有候选文件和配置。
5. 重载 runtime、pipeline、analysis、evidence，确认它们确实加载新代码。
6. 最后才恢复 outbox 消费，让两条 correction 被新 projector 和新 `complete_outbox` 处理。
7. 核对两条新 receipt 的 scope、qualification、Feishu 最终字段和旧 receipt 的历史标记。

### P0-3：“不可变分析身份”定义不一致，会阻断新版本或错误复用旧分析

证据：

- 分析 ID 使用 `transcript_id + transcript_content_digest + analysis_spec_version`（`v3_pipeline_worker.py:472-476`）。
- 新列又把 `model_version`、`prompt_version` 声明为不可变身份。
- 但唯一索引仅为 `transcript_id + analysis_type + analysis_spec_version`（`002_analysis_qualification.sql:14-16`）。
- 创建前去重查询也只检查 `transcript_id + analysis_type + analysis_spec_version`（`v3_pipeline_worker.py:465-469`）。

后果：

- 同一个 transcript 文件内容被合法重写、内容 digest 改变时，分析 ID 会变化，但旧唯一索引会拒绝新行。
- 同一 spec 下升级模型或 prompt 时，旧行会直接阻断新分析。
- 代码认为这些字段属于不可变身份，数据库却把它们排除在版本唯一性之外。

必须统一：

- 明确版本身份的唯一键，并让 analysis_id、数据库唯一索引、创建前查询、lineage upstream_version 使用同一组字段。
- 至少应覆盖 `transcript_id + transcript_content_digest + analysis_spec_version + model_version + prompt_version`；若产品决定 model/prompt 必须随 spec 一起升级，也要在数据库约束和测试中强制该规则，不能只靠约定。

### P0-4：不可变触发器遗漏可导致“已完成正式分析”被换场次或换文件

证据：

- 当前 trigger 仅保护 transcript_id、transcript_content_digest、spec、model、prompt、artifact_digest（`002_analysis_qualification.sql:26-43`）。
- 它不保护 `session_id`、`analysis_type`、`source_digest`、已发布后的 `output_path`。

风险：

- 已 COMPLETE 的正式分析若被改 `session_id`，projector 会把同一正式分析挂到错误场次；COMPLETE 行不会重新进入 analysis worker 的资格校验。
- 改 `analysis_type` 可绕过 single_session 的正式资格映射。
- 改 `output_path` 而保留 artifact_digest，Feishu 会显示另一个文件路径；已 VERIFIED 的 evidence 不会自动复检。

修法约束：

- trigger 应在身份完成绑定后保护这些字段。
- 因 migration 需要把旧 `source_digest` 改成内容 digest，trigger 应在回填后创建，或仅当 OLD.transcript_content_digest 已绑定时才启用相应保护。
- 增加 COMPLETE/已绑定行的负向更新测试。

## P1：应在本次候选中补齐

### P1-1：ALREADY_APPLIED 只看一个版本字符串，数据库漂移会被误报成功

`v3_sample_analysis_migration.py:279-282` 发现 schema_meta=2 就直接返回，不检查列、索引、trigger、回填和纠正 outbox。

必须增加：

- schema fingerprint 或逐项核验；
- 缺列、缺索引、缺 trigger、sample 又变回 COMPLETE、formal 缺 digest、correction outbox 缺失时返回 `DRIFT_DETECTED`，不能返回 `ALREADY_APPLIED`。

### P1-2：plan hash 没有固定 schema 状态，事务也没有固定快照

证据：

- plan core 包含 DDL 哈希和数据分类，但不包含当前列/索引/trigger 签名（`v3_sample_analysis_migration.py:231-244`）。
- apply 使用默认 READ COMMITTED；advisory lock 只有本迁移主动遵守，其他 worker 不会遵守（`v3_sample_analysis_migration.py:275-296`）。

风险：worker 在 build_plan、备份和回填之间写入，plan 可能是混合快照；schema 部分漂移也可能复用旧 plan hash。

建议：

- apply 使用 REPEATABLE READ 或 SERIALIZABLE，并在已暂停服务后执行；
- plan 包含 schema signature；
- 应用前后保存实际代码/DDL/config 哈希；
- 回填前再次核对正式 1 条、样本 2 条及精确 ID。

### P1-3：lineage 计划没有验证“恰好一条 CURRENT 边 + 精确版本”

证据：

- build_plan 只取 `DISTINCT upstream_id`，忽略 `state` 和 `upstream_version`（`v3_sample_analysis_migration.py:155-157`）。
- 生产两个样本各有两条同 transcript、不同 version、且均为 CURRENT 的边。
- 迁移会把样本对应的所有边置 INVALIDATED；这次结果可接受，但计划没有把这个事实作为明确输入或 postcondition。
- 正式分析只要 artifact transcript_id 出现在候选集合里就会被接受，不要求迁移前恰好一条 CURRENT 边。

必须增加：

- plan 输出每个分析的全部 lineage 边（id/version/state）；
- formal 必须恰好一条 CURRENT transcript 边，且迁移后 version 等于 transcript_content_digest；
- sample 迁移后不得剩余任何 CURRENT transcript 边；
- 多 CURRENT、额外 upstream、版本冲突都应进入 issues 并中止。

### P1-4：postcondition 太窄，可能提交“列都在、核心证据仍错”的迁移

现有 postcondition（`v3_sample_analysis_migration.py:332-337`）只检查：

- COMPLETE single_session 是否有若干新字段；
- SAMPLE qualification 的 analysis 状态；
- 列是否存在。

它没有检查：

- 精确 1 formal / 2 sample；
- formal lineage 唯一且 digest 一致；
- sample CURRENT lineage 已清零；
- evidence bundle 已 INVALIDATED_SAMPLE；
- 旧 outbox/receipt 已标 SAMPLE；
- 两条 correction outbox 已创建且 PENDING；
- index/trigger 存在；
- formal artifact/transcript 文件现时 hash 仍匹配计划。

这些都应成为事务内 postcondition，任一失败则回滚。

### P1-5：artifact 迁移识别只验证 transcript_id，不验证 analysis_id/session_id

`artifact_identity()`（`v3_sample_analysis_migration.py:95-105`）没有核对 artifact 中的 analysis_id 与 session_id。

风险：复制错文件但 transcript_id 相同时会被错误绑定，尤其是未来同 transcript 多 spec 的场景。

必须验证 artifact 的 `analysis_id`、`session_id`、`transcript_id` 与数据库行完全一致；新格式还应验证 spec/model/prompt/digest。

### P1-6：evidence worker 没交叉核对三份 digest/身份

`v3_evidence_worker.py:37-87` 只检查分析资格元数据和 bundle.manifest_hash，未确认：

- `analyses.artifact_digest == evidence_bundles.manifest_hash == 文件实际 SHA256`；
- artifact 内的 analysis_id/session_id/transcript_id/digest/spec/model/prompt 与 analyses 行一致；
- CURRENT lineage 恰好一条且版本一致。

这会让数据库几处字段彼此不一致时仍标 VERIFIED。应补交叉验证与负向测试。对本次 legacy formal artifact没有新增嵌入字段的事实，需要显式记录 legacy provenance，而不是假装它是新格式 artifact。

### P1-7：fresh schema 与 002 migration 不一致

`v3_schema.sql` 有新列和一个唯一索引，但没有 002 中的普通索引和 immutable trigger/function。若新环境只调用 `init_db()` 而漏跑 002，会出现“表列存在但没有不可变保护”。

需二选一并测试：

- 所有新库强制运行版本化 migration runner，init_db 不承担升级；或
- fresh schema 与 migration 最终状态完全一致。

### P1-8：没有可执行、验证过的回滚路径

当前 JSON backup 是证据，不是回滚工具。至少应保存：

- 生产 pg_dump（带 SHA256、0600 权限）；
- 回滚 SQL/脚本：恢复被改的 analysis/transcript/lineage/evidence/outbox/receipt，删除未发送 correction，恢复 schema_meta；是否保留新增列和 trigger需明确；
- “migration 成功但代码重载失败”场景的操作顺序；
- 回滚演练结果。
