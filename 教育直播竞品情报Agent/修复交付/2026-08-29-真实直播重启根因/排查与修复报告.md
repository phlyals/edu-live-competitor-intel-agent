# 真实直播 17 次重启根因排查与修复

日期：2026-08-29。目标场次：`session_d832203891613dd5049854db95a78828`，杨文老师讲升学规划。

## 结论

已定位到真实直播中断的直接技术链路：

1. 录制器使用 **HLS**，同一个已解析地址被 FFmpeg 的 HTTP 重连反复使用；直播过程中播放列表与短生命周期分片发生变化。
2. 日志明确出现 `expired from playlists`、HLS 分片 404、playlist reload timeout、时间戳跳变和 demux `Input/output error`。FFmpeg 只会重试原地址，不能重新执行直播间解析取得新的播放地址。
3. 该次严重 I/O error 后 FFmpeg 仍返回 **0**。包装器据“退出码 0 + 存在非空文件”输出 `RECORDED`，把网络/播放列表故障当成正常结束。
4. 后续恢复虽然每次都会重新运行地址解析，但解析器出现 8 次 `not_live`；另有多次 FFmpeg 取得空 HLS，运行约 120 秒无文件增长后被守护器 SIGTERM。原有 30 秒/600 秒退避把这些失败扩展成较大缺口。

**最可能根因是 HLS 播放列表/分片失效与刷新超时，而不是本地编码或资源问题。** 没有发现 401、403、429，也没有逐次变慢的自然趋势，因此没有证据支持 IP 封禁或限流。404 位于 HLS 分片，不足以单独证明鉴权 token 过期。

修复为：真实直播优先使用连续 **FLV**；每 900 秒主动结束当前小段并重新解析一次流地址；不再对 HLS EOF 循环复用旧 URL；解析器连续三次判定离线后才结束；每段保存不含 token 值的地址指纹。回放验证与 95 项回归均通过，最终仍须等待修复后新开的真实直播。

## 二、流地址稳定性

### 是否每次重新解析

是。每个 `RECORDING_PROCESS_STARTED` 都新启动 Profile recorder；共享 recorder 的 `main()` 在启动 FFmpeg 前调用 `resolve_stream()`，没有从数据库或上一次进程缓存 URL。因此 17 次恢复都**尝试**重新解析。

但“重新调用解析器”不等于“拿到可用新地址”：8 次明确返回未开播，后续多次拿到的 HLS 是空分片或无法解析 codec。

### 第一次和最后一次地址能否比较

不能从历史证据恢复。上一轮修复为了不泄露 token，把 stderr 中 URL 整体替换成 `<stream-url>`，同时没有保存不可逆指纹；上游 PlayURL 日志也为空。现有证据无法诚实回答：

- 第一次和最后一次 hostname 是否相同；
- path 是否相同；
- token/signature 是否变化或过期。

本次新增 `stream_fingerprint`，只保存 scheme、hostname、path SHA-256、query key 名称以及 query/url SHA-256，不保存 query 值。后续能够比较域名、路径和鉴权集合是否变化，又不会暴露 token。

### 地址失效判断

可确认 **HLS 分片和 playlist 状态失效**：404、expired segments、playlist reload timeout 均为直接证据。无法进一步确认“根 URL 鉴权 token 过期”，因为没有原 URL、过期字段或 401/403 证据。

## 四、修复

### 1. 优先 FLV

Douyin resolver 同时提供 FLV 和 HLS。旧代码的 `record_url` 实际优先 HLS；新代码显式按 FLV、HLS 排序。FLV 是连续 HTTP 流，避免逐个短生命周期 HLS 分片的 404/过期窗口。HLS 仍保留为可诊断的候选信息，不再作为首选。

### 2. 定时刷新真实流地址

Profile 配置新增：

```json
"recording_stream_refresh_seconds": 900
```

真实直播每 900 秒关闭当前媒体小段，重新请求直播间并解析新地址，再写入唯一 `refreshNNNN` 小段。最终仍由原 finalizer 无转码合并为一个 `整场直播.ts`。回放文件不走刷新循环，保持原逻辑。

单个小段不足 895 秒或 FFmpeg 非零退出时，不再宣布整场完成：重新解析并继续，连续三次失败才交回守护器退避。解析器也必须连续三次离线才把已有录制视为自然结束，避免单次 false negative。

### 3. 移除 HLS EOF 旧地址循环

删除 `-reconnect_at_eof 1`。保留有限的网络错误、429/5xx 重连，用于短抖动；地址生命周期问题通过 900 秒重新解析解决。

### 4. 保留逐次证据

- 每个刷新段使用唯一文件和唯一 sidecar。
- Profile 选择续录文件名时，同时检查媒体和 sidecar，零字节失败也不会覆盖旧诊断。
- sidecar 记录安全地址指纹、解析时间、协议、FFmpeg 退出码和最后 50 行脱敏 stderr。
- stdout 记录每个内部流尝试，便于未来逐次形成退出表。

### 5. 不建议更换 IP

没有封禁证据，更换 IP 会增加权限、稳定性和合规风险，当前不执行。若未来安全指纹显示同一地址在不同时间持续收到明确 403/429，再单独评估请求频率和平台访问策略。
