# 900 秒刷新交接空档：隔离候选报告

## 状态

**不可上线，待第二项完成后重基线。** 本轮只在本目录复制件上开发和测试；未修改生产 Profile、共享录制器、数据库、服务或媒体，也没有等待真实 900 秒。

## 根因

基线 `record_douyin_live.py:337-340` 的顺序是：当前 FFmpeg 退出 → `ffprobe` → 重新解析地址 → 启动下一 FFmpeg。因此解析地址的时间必然处于无采集窗口。生产证据显示 20 个相邻刷新空档合计 57.647 秒，中位 1.868 秒，最大 8.949 秒。

## 最小候选

候选补丁只改共享录制器的复制件：

1. 当前 900 秒段结束前 30 秒，用 daemon 线程预解析下一条签名地址；
2. 只有预解析结果仍为 LIVE 且含流地址时才缓存；否则继续使用原按需解析路径；
3. 下一段仍在旧 FFmpeg 退出后启动，任一时刻每个房间只有一个 FFmpeg；
4. sidecar 只写安全指纹、`resolved_at` 和 `resolution_source`，不落原始 token；
5. 当前段提前失败时取消预解析，不改变现有三次失败、离线确认和退避逻辑。

候选文件为 `candidate/record_douyin_live.py`，可应用差异为 `candidate-preresolve.patch`。

## Trade-off

- 这只是**减少空档**，不是消除空档。旧进程退出、Python 调度、`ffprobe` 和新 FFmpeg 建连仍然是顺序执行，所以不能据此宣称无缺口或录制完整。
- 签名地址会提前约 30 秒取得，实际使用时比按需解析更旧；若平台 token 极短，可能在使用前失效。现有失败恢复会重新解析，但仍会产生一次失败尝试。
- 每个活跃房间多一个休眠 daemon 线程，并在刷新前多一次解析请求；不会同时运行两个 FFmpeg，资源增量较小，但高并发下仍需压测。
- 预解析的瞬时错误不终止录制，而是回退按需解析；这保留可用性，但会保留原交接空档。
- 不回填历史场次，也不改变历史 completeness、gap 或起止时间。

## 是否必须双 FFmpeg 重叠

首个候选**不应立即上双 FFmpeg**。若目标是把本地“无人采集”的区间真正压到接近零，最终很可能需要短重叠或单一可刷新输入代理；仅预解析做不到。

双 FFmpeg 的副作用明显：短时双倍连接和带宽、65 路上限附近额外进程压力、平台限流风险、重叠音视频重复、PTS/DTS 不连续，以及 finalizer 必须新增按时间戳或内容去重。当前 finalizer 只做顺序拼接，直接引入重叠会把重复内容写进整场文件，因此本轮不采用。
