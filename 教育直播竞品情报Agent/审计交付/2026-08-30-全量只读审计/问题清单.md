## 三、P0：应立即阻断“生产已就绪”结论

### P0-1 下播增长保护会永久锁住场次，并已出现跨直播拼接

[`v3_worker.py:189`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_worker.py:189) 检测到目录字节大于旧基线后否决离线，但不把基线更新为当前值；recorder 已死且目标离线时，后续分支又不再采样。当前两场 PID 为空、目标已离线，却被固定尾部字节差反复否决：

- 高考通：固定差 50,448 字节，累计 61 次拒绝；
- 方老师：固定差 177,092 字节，累计 4 次拒绝。

历史上已出现同一业务场次两段采集相隔 14,546.81 秒，之后仍被合并进同一个 `整场直播.ts`。这会阻止自然结束、阻塞转录，并可能把下一次开播续进上一场。

### P0-2 retention 可用 300 秒样本放行整场视频删除

[`v3_retention_worker.py:45`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_retention_worker.py:45) 对视频只要求存在任意 `status='COMPLETE'` 转录及其 `source_path`，不要求：

- `coverage_scope=FULL_SESSION`；
- 场次连续完整；
- 分析完成且证据包 VERIFIED；
- 飞书回执、人工复核、审批完成；
- 最近两场保留和 3 天缓冲等 Profile 约束。

pipeline 恰好会把 300 秒样本标成 `COMPLETE`。删除路径直接信任 payload，也没有受控根目录或 manifest hash 校验。当前生产文件尚未被误删，但这是一个即将进入时间窗口的不可逆风险。

### P0-3 生产门禁 fail-open：门禁失败但全自动生产仍运行

实际状态同时为：

- `production_gate=BLOCKED`；
- `tenant_verification=BLOCKED_MISSING_SCOPE`；
- `ready=false / final_ready=false`；

- `atomic_activation=ACTIVE`、`BRIDGE_FULL_FLEET_ACTIVE`、七项 routine automation 全开。

[`v3_worker.py:90`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_worker.py:90) 的 activate 只检查 `ready`，不检查 `final_ready`、租户或 production gate；状态跌出 readiness 后也不会自动降级。当前 9 个相关 LaunchAgent 均实际在运行，不是单纯的显示问题。

### P0-4 PostgreSQL 本机访问等同无鉴权超级用户

PostgreSQL 虽只监听 localhost，但 Unix socket、127.0.0.1 和 ::1 全部为 `trust`；Runtime 使用的角色同时具备 superuser、createdb、createrole、replication、bypassrls。43 张表没有一张启用 RLS。任何本机进程都可以无口令冒充超级用户并修改该库及其他数据库。

此外，系统盘和外置 USB APFS 均未加密；生产媒体、转录、分析及有效凭据落在该外置卷。文件权限多数正确，但设备遗失时权限无法替代静态加密。

### P0-5 无可恢复备份，单点故障会同时丢控制面和业务材料

- Time Machine 没有 destination，录制目录明确被排除；
- PostgreSQL `archive_mode=off`、`data_checksums=off`；
- 未发现 pg_dump/basebackup 定时任务或恢复演练；
- 所谓 SQLite mirror 停留在 8 月 25 日，数据规模为 tasks=0、sessions=6、transcripts=0、analyses=0，远落后于生产 PostgreSQL，不能恢复当前状态；
- 单台 M1/8GB Mac、单 PostgreSQL、单外置盘均无副本。

### P0-6 PostgreSQL claim/fencing 不具备互斥性，可能重复执行与重复投递

[`v3_runtime.py:216`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_runtime.py:216) 的 `BEGIN IMMEDIATE` 在 PostgreSQL 兼容层变成普通 `BEGIN`。task/outbox claim 都是无锁 SELECT 后 UPDATE，没有 `FOR UPDATE SKIP LOCKED` 或条件 `UPDATE ... RETURNING`。完成/重试也不校验 owner 或 fencing token。

outbox lease 仅 120 秒，但实际投影 subprocess 允许 180–900 秒，而且从未续租。进程重叠时，同一任务可被两个 worker 同时领取，旧 worker 还能覆盖新 owner 的状态或重复向飞书投影。

### P0-7 analysis 与 transcript 没有不可变版本绑定

`analyses` 没有 `transcript_id` 外键；[`v3_analysis_worker.py:270`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_analysis_worker.py:270) 仅按 `session_id` join。一个场次有多个完成转录时，同一 analysis 会反复匹配并覆盖同一路径，artifact、evidence、lineage 可能分别指向不同版本。

pipeline 又以“场次存在任意非 SKIPPED analysis”为阻断条件。现有样本 analysis 会挡住未来真正的 `FULL_SESSION` 分析。

## 四、P1：已影响正确性、完整性或持续运行

### P1-1 `restart_count=0` 不能证明完整，5 场新实播全部仍为 PARTIAL

修复后的 5 个自然结束、无 supervisor 重启场次，媒体/观测时长分别为 93.66%、95.69%、95.35%、94.75%、86.25%，全部由 Runtime 标为 `PARTIAL`。其中 95.69% 和 95.35% 会被原 5% 验收脚本判为 PASS。

原 [`check_recording.py:19`](/Users/mac/Documents/agent架构师/教育直播竞品情报Agent/验收脚本/check_recording.py:19) 只比较容器时长，不读 `recording_gap_seen`、sidecar、restart、FFmpeg tail 或连续采集证据。已有真实场次 `session_1f8537...` 被脚本判 PASS，但数据库明确记录 `completeness=PARTIAL`、`continuous_capture=false`、`recording_gap_seen=true`。

### P1-2 900 秒刷新产生未登记盲区

5 个无重启场次共有 20 个刷新交接空档，合计 57.647 秒，中位 1.868 秒，最大 8.949 秒。当前实现先结束旧 FFmpeg，再 ffprobe、解析 URL、启动新 FFmpeg，没有预解析或重叠交接。这些空档既未写入 `recording_gaps`，也不一定设置 `recording_gap_seen`。

### P1-3 `return_code=0` 仍包含严重媒体错误，完整性规则不消费

近期 sidecar 固定快照中有 26 个 `return_code=0`，但 stderr tail 含 404、premature end、demux I/O、invalid data 或 packet mismatch。finalizer 只看输出非空和容器时长；音频/视频 map 都是可选，缺一条流仍可能形成文件。

### P1-4 finalizer 证据不足即删除源分段

[`v3_worker.py:445`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_worker.py:445) 仅按 mtime 排序分段；concat 成功且输出非空就立即删除源媒体。manifest 不保存源分段顺序、哈希、时长、sidecar、退出码或 gap。一场最终 TS 的全包只读检查仍出现 non-monotonic DTS；115 个归档 sidecar 的 output_path 已失效。

### P1-5 274 条 segment 路径失效，制造 245 条永久假转录任务

334 条 `recording_segments` 中只有 60 条路径存在；274 条路径已失效，其中 245 条仍标 `COMPLETE`。这些大多是合并后被删除的旧分片，但数据库没有 `SUPERSEDED/MERGED` tombstone。

245 条 `WAITING_TOOL` transcript 与这些失效 COMPLETE 分片一一对应，源文件和输出均不存在。pipeline 每轮仍扫描它们，7 个场次被膨胀成 245 条永远无法恢复的任务。

### P1-6 当前没有整场生产转录，heartbeat 却长期显示 READY

250 条 transcript 中 245 条为上述 `WAITING_TOOL`；5 条 COMPLETE 中，3 条是历史导入、2 条是 300 秒 `sample_only=true`，`FULL_SESSION` 数量为 0。pipeline heartbeat 仍返回 READY/本轮 transcripts=0，因为它不把这些永久失败计入健康状态。

生产 COMPLETE 的判断只验证 ASR 自报输入时长接近音频时长，不计算时间戳区间并集，也没有覆盖率门槛。因此即使未来产生 `FULL_SESSION` 标签，仍不等于时间戳覆盖达到 90%。

### P1-7 两份样本被冒充为正式分析全链路发布

两份 300 秒样本已经产生 `analyses.COMPLETE/CURRENT`、`evidence_bundles.VERIFIED` 和 `semantic_projection.SENT`。evidence worker 只校验文件 hash，不校验 schema、范围、事实或证据内容。飞书中用户看不到 SAMPLE/FULL_SESSION 差别。

当前生产库没有一份新修复格式的整场分析；本地仅有两份 8 月 25 日旧样本分析。8 月 29 日 68KB 的修复验证结果是隔离模拟产物，没有进入生产控制面。

### P1-8 analysis coverage 指标可虚报，且没有 90% 完成门槛

[`v3_analysis_worker.py:198`](/Users/mac/.hermes/profiles/edu_live_competitor_intel/runtime/v3/v3_analysis_worker.py:198) 用“最后时间戳减第一时间戳”当 timeline coverage，中间任意大 gap 都被吞掉；`segment_coverage_rate` 被硬编码为 1.0。状态写 COMPLETE 前没有 `<0.9` 拒绝逻辑。

验收脚本也有同类缺口：只读构造 1% 转录覆盖、七个模块全部引用同一秒，`check_analysis.validate()` 仍返回 `PASS/is_complete=true`。它验证“引用落在已覆盖区间”，没有验证总体覆盖率、模块内容、引用唯一性或证据是否支持摘要。

### P1-9 模型时间戳没有绑定原始 segment

chunk validator 只要求模型时间在 chunk 首尾之间；如果时间落在 chunk 内部的真实 gap，merge 会把它强行贴到最近一条原文。模型应返回 source segment ID，由程序回填原始 start/end/text；当前做法仍可能把臆造时间变成看似可审计证据。

### P1-10 analysis/pipeline 长任务没有 claim，外部错误重试也不完整

analysis 和 ASR 都在长时间 API/模型调用前保持 PENDING/WAITING 状态，没有 owner、lease 或 CAS。多实例或重启重叠会重复调用并覆盖结果。

DeepSeek 的网络、HTTP 状态或 response JSON 异常发生在重试 try 之外，只会立即退出；三次重试仅覆盖“模型正文不是合法业务 JSON”。长分块处理期间也不续心跳。

### P1-11 lineage 和 recompute 是死链

analysis 的 upstream version 实际是 `sha256(output_path 字符串)`，不是 transcript 内容、模型、prompt 或 schema 版本。两个样本 analysis 已各有两条不同 upstream version、但同时标 CURRENT 的 lineage edge。

代码中没有生产者把 edge 标 STALE；即使人工置为 STALE，recompute 只把分析置 STALE 并建 review，analysis worker 又不领取 STALE，pipeline 也因“已有 analysis”拒绝新建。不会发生真正重算。

### P1-12 evidence/outbox 的顺序和版本去重错误

analysis 在 evidence bundle 仍为 REQUIRED 时就 enqueue 飞书投影；投递端不等 VERIFIED。outbox payload 只有稳定 analysis_id，内容变更后仍命中旧 SENT dedupe key，不会重新投影新版本。

outbox SENT 与 task COMPLETE 分属两个事务，进程在中间崩溃会留下永久 `DELIVERY_PENDING`；当前没有 reconciler。

### P1-13 核心业务目标“最近两场比较→打法版本→策略→正式知识”尚未实现

Runtime 中没有生产 comparison worker、连续三场版本确认、strategy 生成、Knowledge Diff 或批准后写入逻辑。现有：

- 3 个 strategy candidate 全是历史导入、`PENDING_REVIEW`、content_path 为空；
- approvals=0；knowledge_diffs=0；唯一 knowledge version 为 DRAFT；
- “直播竞品知识库”目录为空；
- review_items 只有一条 ASR 复核，没有三条策略对应的审核项。

当前真实闭环最多到“单场分析的早期样本”，还没有达到 Agent 岗位卡定义的竞品策略闭环。

### P1-14 ASR 准确率质量门尚未完成

唯一人工复核项仍 PENDING。现有样本 CER 约 16.1%、术语召回约 66.7%；所谓参考稿本身也是 Whisper-base 机器稿，不是独立人工金标。系统也没有 speaker diarization，分析仅凭文字判断当前讲师，讲师字段的可靠性没有验收基础。

### P1-15 全文逐字稿会原样发送到外部模型，没有 PII/敏感字段过滤

转录在本地完成，但分析会把带时间戳逐字稿分块原样发送给 DeepSeek。没有姓名、手机号、学生信息、评论区内容的脱敏或数据出境开关，也没有按字段最小化。教育直播可能包含未成年人和家长信息，这需要明确的数据治理边界。

### P1-16 Runtime 守护进程仍可被单个 `/bin/ps` 超时杀死

每个 job 重复执行全量 `ps -axo`，超时未捕获；daemon 主循环没有每轮/每场异常隔离。日志已有 30 次这种未捕获超时，runtime launchd 历史 `runs=60,last exit=1`。pipeline 也有 `runs=34,last exit=1`。

heartbeat 的 `finalized=68` 是每轮重复遍历终态 job 的数量，不是新完成数量，容易掩盖故障。

### P1-17 磁盘上的最新代码并未全部加载到常驻进程

- pipeline PID 91389 启动于 8 月 28 日 23:35:45，`v3_pipeline_worker.py` mtime 为 23:36:27，晚 42 秒；该进程仍运行旧内存代码。

## 五、P2：中期治理与可维护性问题

### P2-1 数据库约束弱

public schema 没有 CHECK constraint；状态、时间、JSON 均为 TEXT。generic lineage/evidence/retention/outbox 缺少外键，时间同时混用 `Z` 与 `+08:00`，部分代码直接按字符串排序比较。当前抽查 8,001 个 JSON 值均可解析，核心 FK 也未发现现存孤儿，但 schema 无法阻止未来错误。

### P2-2 状态语义复用过多

`COMPLETE` 同时可表示最终媒体、已删除源分片、300 秒样本转录和历史导入；`VERIFIED` 既可表示文件 hash 正确，也被用户理解为业务完整。58 个 PARTIAL 场次 manifest 全是 VERIFIED，303 个 PARTIAL 场次 segment 仍是 COMPLETE。应把 artifact lifecycle、coverage qualification、semantic qualification 分列。

### P2-3 失败状态没有终态收敛

8 个 `ENDED/UNKNOWN` 场次的 job 仍为 `WAITING_STREAM`，历史 restart 达 3–753；没有 FAILED_FINAL/quarantine/人工告警。另有两个无 recording_job 引用的历史 partial 媒体目录，合计约 2.66GB；当前 retention 无法按血缘处理。

### P2-4 HLS fallback 只存在于候选数据，不存在于执行路径

共享录制器会生成 FLV/HLS candidates，但实际每次只消费第一个 FLV。近期 132 个 sidecar 全是 FLV，出现 404/I/O 时没有一次 HLS fallback 证据。

### P2-5 共享 cookie、argv 和日志隐私面仍偏大

共享 0644 配置含非空抖音 cookie，vendor 源码还有内嵌 cookie 默认值；FFmpeg 进程 argv 包含完整签名 URL。持久化 sidecar/recorder.log 未发现原始 token，这是有效防护，但本机进程观察者仍可从 argv 读取。

Agent 日志中仍有 open_id、chat_id、message_id、完整 inbound 记录和大量 URL，与 `redact_pii=true` 不一致。主要 secret 文件为 0600，抽查未发现 Feishu/DeepSeek 密钥泄漏到日志，这是正向事实。

### P2-6 源码、规范和部署来源不统一

生产 Profile 不在 Git 仓库内；项目仓库只跟踪少量文档/补丁，分支 ahead 3，后续多份修复报告和分析补丁仍未跟踪。数据库没有 release 记录。

生产 `SOUL.md` 与项目 `04-Profile.md` hash/行数不同；SOUL 有 16 行生产扩展没有回写项目规范。Hermes `config.yaml` 的通用 checkpoints 还处于 disabled，而 Profile 明确要求长期任务可恢复。必须确定唯一规范源和 deployment revision。

### P2-7 工具与共享依赖漂移

lark-cli 为 1.0.58，工具提示已有 1.0.92；CUA 为 0.20.0，日志提示至少 0.22.2。Feishu V3 ingress 直接补丁到共享 Hermes gateway 源目录，该目录没有可重放的 Git/patch 记录，Hermes 更新可能覆盖入口。

### P2-8 心跳和节点记录语义不可靠

非 runtime worker 的 heartbeat `started_at` 不随重启更新；Feishu ingress 记录的是短命健康 helper PID，查询时通常已退出；`worker_nodes` 只有一行，被最后一个写入服务覆盖，不能表示每个服务或备用节点。状态应区分 owner PID、probe PID、实例 ID 和服务版本。

### P2-9 验收脚本及测试仍有覆盖盲区

55 项验收测试和 104 项 Runtime 测试全部通过，但没有覆盖：

- 真实 PostgreSQL 多 worker claim/fencing；
- 1% transcript coverage 仍能通过 analysis completeness；
- 真实 sidecar gap/FFmpeg tail/PTS 连续性；
- production/tenant/capacity gate 阻断；
- 文件修改后的受控 reload 和 loaded hash；
- 外置盘未挂载、日志轮转、恢复演练；
- 多个不同远端源的长时容量；
- 真实飞书/CUA 断线恢复。

自检报告在失败时只生成文件，不会阻止 full fleet；历史 `final-self-check.json` 已明确 FAIL 32/38，但系统仍 ACTIVE。

### P2-10 outbox 存在少量未收敛账务

当前 267 SENT、1 DEAD_LETTER；有 1 个 SENT 没有独立 delivery receipt。旧 LIVE 投影死信后来已被 OFFLINE 状态覆盖，但死信没有标 superseded。当前 payload hash、JSON 和 lease 没发现普遍异常。

## 六、已确认有效的部分

为避免把审计写成“全坏”，以下防护本轮确实成立：

- 58/58 当前 manifest 文件存在且 SHA 匹配；60 个现存 segment 的数据库 bytes 与 stat 一致。
- 抽查 8,001 个 JSON 文本值均可解析；核心 FK 未发现当前孤儿，未发现重复媒体路径/校验和。
- 近期 132/132 sidecar 均有唯一 `url_sha256` 和 `resolved_at`，持久化文件未发现原始签名 token。
- profile 根目录 0700，主要 secret/config 0600；日志扫描未发现 Bearer、PostgreSQL DSN、Feishu/DeepSeek secret 泄漏。
- PostgreSQL、gateway、CUA socket 和 9 个相关 LaunchAgent 在审计时在线；没有旧 profile 业务进程。
- 外置盘还有约 551GiB 可用，当前不是外置媒体盘容量事故。
- pipeline 对 `PARTIAL` 或 `continuous_capture!=true` 的整场媒体保持了阻止正式 ASR 的安全门，这一条不应放宽。
