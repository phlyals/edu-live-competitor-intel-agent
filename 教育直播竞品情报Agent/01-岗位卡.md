# 01-岗位卡 V1.0 正式版：教育直播竞品情报与话术优化 Agent

## Agent 岗位卡

### 岗位名称

直播竞品情报主管

### 一句话岗位定义

当收到一个5元教育课包商品链接时，自动在已登录的巨量百应中完整找到并持续维护该商品对应的带货同行集合，将同行及带货信息维护到飞书；持续监控并录制同行每一场直播，完成转录、最新两场场次对比、话术打法版本追踪和竞品策略提炼，再结合我的正式直播知识库生成待审核的话术优化方案，经人工确认后更新正式知识库并生成新版原创直播话术。

---

## 五维筛选结果

反复出现：是。

输入稳定：是，核心任务输入为5元教育课包商品链接。

流程明确：是，主要流程为：

商品 → 持续发现同行 → 监控 → 录制 → 转录 → 场次比较 → 打法版本追踪 → 分析 → 优化 → 审核 → 更新。

输出清晰：是，可以通过飞书记录、逐字稿、竞品分析、优化方案和正式话术验收。

人工可兜底：是，登录、验证码、平台异常、策略判断和正式知识更新均有人工作为最后控制点。

综合判断：**5/5，非常适合 Agent 化。**

## 输入

### 核心任务输入

一个5元教育课包商品链接。

来源：

用户通过飞书发送给 Agent。

### 工作所依赖的资源

以下内容不是每次任务都重新输入，而是 Agent 长期工作的基础环境：

- 已人工登录的巨量百应浏览器环境；
- 飞书多维表格和飞书文档；
- 本地 Obsidian Vault；
- 位于 Obsidian 中、受人工审核保护的正式直播话术知识库；
- 本地直播媒体存储目录。

## 处理动作

### 1. 首次发现并持续维护同行集合

商品首次接入时，根据用户提供的商品链接进入巨量百应对应商品页面。

完整遍历当前账号权限和页面可见范围内，该商品对应的同行结果列表。

获取并整理：

- 同行账号名称
- 达人 ID / 账号 ID
- 直播间地址
- 商品关联关系
- 平台当前可见带货数据
- 发现时间
- 最近更新时间

只有商品对应同行列表已经完整遍历并完成去重，才能把本次同行扫描标记为完成。

账号名称不能单独作为唯一标识，应优先使用稳定的平台达人 ID、账号 ID 或其他平台唯一 ID。

同行发现不是一次性任务。

首次扫描完成后，主管 Agent 仍需周期性重新进入巨量百应，完整扫描该商品当前对应的同行结果。

重新扫描时：

- 新发现的同行自动写入飞书并加入监控；
- 已存在的同行更新最新状态；
- 商品与同行之间的关系变化需要留下记录；
- 不得因为第一次扫描完成，就永久停止该商品的同行发现。

如果后续扫描发现某同行已不再出现在该商品对应的同行结果中，不删除同行账号、商品带货关系历史或已有业务数据，而是更新该“商品 × 同行”关系的当前状态并保留历史变化。是否暂停该关系对应的监控，留到后续工作流阶段制定规则。

具体重新扫描频率留到后续工作流关卡确定，本岗位卡不作规定。

### 2. 建立并维护同行监控名单与商品带货关系

将发现的同行及相关数据写入飞书。

- 已有同行更新最新身份和账号状态；
- 新同行新增记录并进入监控范围；
- 以稳定的平台账号 ID 作为主要去重依据；
- 保存数据采集时间和最近更新时间。

必须区分“同行身份”和“商品带货关系”。

同行身份包括：

- 达人 ID
- 账号 ID
- 名称
- 直播间
- 账号状态

某个同行针对某个商品的带货关系及平台可见带货数据，则属于“商品 × 同行”这一关系的数据。

系统需要维护商品与同行之间的关系，并保存必要的历史变化，确保后续能够回答：

- 某个同行什么时候开始带这个商品；
- 最近是否仍在带；
- 平台可见带货数据如何变化；
- 同一个同行是否关联多个商品。

不能把所有商品的带货数据永久覆盖在同行账号主记录中。

具体采用关系表、快照表或其他结构，留到后续工作流和飞书数据设计阶段确定。

飞书作为用户查看同行、场次、变化、策略和审核状态的唯一主要工作台。

### 3. 持续监控并完整录制直播

持续监控目标同行的开播状态。

只要同行开始直播，就触发录制。

每一场直播都应尽可能从检测到开播开始，持续录制到主播下播。

不得因为最近两场直播内容高度相似而停止后续完整录制，也不得改为只录制直播前20分钟。

如果检测到直播时已经错过开头，或录制过程出现无法恢复的内容缺失，必须标记为部分录制，不能将其虚报为完整场次。

录制异常允许重试。后续转录或分析失败时，不得删除已经成功录制的素材。

### 4. 自动转录并沉淀竞品原始素材

直播结束后自动执行：

录像  
→ 音频  
→ Whisper / faster-whisper 转录  
→ 带时间戳逐字稿  
→ 清洗版逐字稿。

原始录像、音频和逐字稿属于竞品原始证据。

分析结果必须能够通过来源场次和时间戳回到真实直播内容。

关键内容无法可靠识别时，应标记低置信度并提交人工确认，不能直接作为确定事实。

### 5. 比较最新两场直播并追踪话术打法版本

每个同行产生新的可用完整直播后，重点比较：

最新完整场 N  
VS  
上一完整场 N-1。

部分录制场次仍应保留场次记录，可以进行带有完整性说明的辅助分析，但不能在未说明的情况下替代完整场次进入正式场次比较链。

比较时不能只计算整篇逐字稿的总相似度。

应区分：

- 固定讲解内容
- 干货知识内容
- 家长需求建立
- 信任建立
- 商品介绍与承接
- 成交推动
- 用户答疑
- 临时闲聊

重点追踪固定业务内容的变化。

答疑天然具有随机性，不应因为答疑不同就判断整个直播话术已经重大改版。

每次比较至少记录：

- 整体相似度
- 固定讲解相似度
- 干货内容相似度
- 商品承接相似度
- 新增内容
- 删除内容
- 修改内容
- 内容顺序变化
- 商品首次出现时间变化
- 商品承接方式变化
- 新主题
- 新策略
- 本场变化摘要

80%只作为辅助判断主体是否稳定的指标，绝不是停止下一场完整录制的条件。

如果主体内容稳定，但商品承接发生明显变化，必须单独标记，不能被总相似度掩盖。

直播场次和话术打法版本是两个不同概念。

连续多场直播即使场次不同，只要固定讲解结构、干货、需求建立、信任建立和商品承接等核心内容基本稳定，就可以属于同一个话术打法版本。

只有出现明确的核心打法调整时，才形成新的话术打法版本。

是否升级版本的具体判定规则，留到后续工作流阶段设计。

### 6. 提炼竞品策略候选

Agent 根据真实直播、场次变化和话术打法版本演进，提炼：

- 新的直播主题
- 新的开场钩子
- 家长痛点
- 需求建立方式
- 信任建立方式
- 干货结构
- 商品承接方式
- 成交推动方式
- 稳定长期打法
- 可能只是临时测试的表达

所有新发现首先进入竞品策略候选库。

必须记录：

- 来源同行
- 来源场次
- 来源时间戳
- 原始证据
- Agent 判断
- 与历史场次及打法版本的关系
- 当前人工审核状态

候选策略不能自动进入正式知识库。

模型对同行调整原因的判断属于分析或推断，不能表述为已经验证的事实。

### 7. 与正式知识库比较并提出优化

读取：

竞品策略候选  
+  
我的正式直播知识库。

重点判断：

- 我的现有内容已经有哪些；
- 同行最近新增了什么；
- 我的哪些内容可能需要更新；
- 哪些同行方法值得测试；
- 哪些方法不适合我的业务；
- 哪些内容应继续观察。

Agent 生成话术修改建议，但不得直接修改正式内容。

修改建议必须明确展示：

原内容  
→  
建议内容

并记录：

- 修改类型
- 修改原因
- 竞品依据
- 来源同行
- 来源场次
- 来源时间戳
- Agent 判断
- 风险
- 置信度
- 建议采用、观察或不采用

### 8. 人工审核并更新正式知识

任何新的策略和话术修改必须先由用户人工审核。

未经明确批准，不得进入正式知识库。

人工批准后，创建新版本和实际写入正式知识库的动作可以由 Agent 自动执行，并记录写入结果、修改内容和版本关系。人工负责最终审批决策，不要求人工承担重复的文件写入操作。

用户批准后：

- 创建新的正式话术版本；
- 保留旧版本；
- 保存修改内容、修改来源和版本关系；
- 基于最新正式知识生成新的原创直播方案。

用户拒绝或纠正建议时，应记录拒绝原因和审核意见，供后续分析参考。

最终是否真正投入直播仍由用户决定。

## 数据与知识库架构

### 1. 飞书

定位：

用户唯一主要工作台，以及业务查看、状态跟踪、任务控制和人工审核的主要入口。

飞书是以下结构化业务数据的主数据源：

- 商品
- 同行身份
- 商品与同行的带货关系
- 平台可见带货数据及必要的历史变化
- 开播状态
- 直播场次
- 话术打法版本
- 任务状态
- 相似度
- 变化摘要
- 审核状态
- 是否采用
- 操作记录

一个飞书多维表格 Base 至少包含以下六张核心表：

1. **商品库**：保存商品及其扫描、同行数量和监控状态。
2. **同行账号库**：保存同行身份、平台 ID、直播间和账号状态。
3. **直播场次库**：保存直播场次、时间、录制及转录状态、场次比较和相关分析。
4. **竞品策略候选库**：保存策略内容、来源证据、Agent 判断、审核状态和采用情况。
5. **话术优化审核库**：保存原话术、建议内容、修改原因、竞品依据、审核意见和正式版本关系。
6. **我的正式话术库**：保存正式主题、结构、话术模块、版本、生效时间和历史版本关系。

商品与同行之间的带货关系必须作为区别于同行身份的独立业务对象进行维护。

具体采用关系表、快照表还是其他结构，留到后续工作流和飞书数据设计阶段确定。

多维表格负责结构化数据，不承载几万字的完整逐字稿。

### 2. Obsidian

定位：

Agent 的本地长文本知识底座。

Obsidian 是以下长文本的主数据源：

- 当前保留的完整逐字稿
- 清洗版逐字稿
- 完整竞品分析
- 竞品策略正文
- 我的完整正式直播话术
- 正式知识库长文本
- 正式话术历史版本

正式知识库的历史版本长期保留，不适用竞品“最近两场重素材”清理规则。

### 3. 本地媒体仓库

定位：

大型原始媒体文件的主存储位置。

主要保存：

- 直播录像
- 直播音频
- 录制分段文件
- 其他大型媒体文件

不将所有大型直播视频上传到飞书，也不将视频存入 Obsidian Vault。

### 4. 飞书长内容查看原则

虽然长文本真本保存在 Obsidian，飞书仍必须成为用户完成日常查看和审核的唯一主要工作台。

对于每个同行当前保留的最近两场完整直播，飞书必须提供可直接进入的完整内容、分析结果、版本比较、优化建议和审核入口。

Obsidian 负责保存长文本真本，但用户日常不应依赖进入本地 Obsidian 文件夹查找业务内容。

历史旧场次的完整重素材被清理后，飞书仍须长期保留：

- 场次
- 版本
- 相似度
- 变化摘要
- 关键证据摘要
- 策略
- 审核结果
- 是否采用
- 对正式话术产生的影响

三层存储不进行无规则的完全双向同步。出现不一致时，以对应数据类型规定的主数据源为准。

## 版本追踪机制

### 1. 最新两场场次比较

每个同行的场次比较基于最近两场可用完整直播：

最新完整场 N  
VS  
上一完整场 N-1。

每产生一场新的完整直播，都必须与上一完整场比较并生成场次变化记录。

这属于直播场次比较，不代表每产生一场直播就自动创建一个新的话术打法版本。

### 2. 两条独立演进关系

系统需要长期维护两条不同的演进关系。

第一条是直播场次演进：

场次31  
→ 场次32  
→ 场次33  
→ 场次34

第二条是话术打法版本演进：

V6  
→ V7  
→ V8

多个连续直播场次可以归属于同一个话术打法版本。

逐字稿、直播录像、场次比较和相似度属于判断话术打法版本的证据，不等同于话术打法版本本身。

### 3. 话术打法版本

当连续多场直播的核心业务内容基本稳定时，可以判断这些场次属于同一个话术打法版本。

核心业务内容包括：

- 核心直播结构
- 固定讲解主题
- 干货模块
- 需求建立方式
- 信任建立方式
- 商品承接方式

只有后续场次出现明确的核心结构或关键打法调整时，才形成新的话术打法版本。

每个话术打法版本至少需要能够说明：

- 从哪一场开始
- 当前持续了多少场
- 核心直播结构
- 固定讲解主题
- 干货模块
- 需求建立方式
- 信任建立方式
- 商品承接方式
- 与上一版本最大的变化
- 当前是否仍在使用

具体如何自动判断是否升级版本，留到后续工作流阶段设计。

### 4. 长期演进记录

即使旧完整素材已经清理，也必须长期保留同行的话术打法版本演进，例如：

- V1 → V2：新增某个直播主题；
- V2 → V3：删除某段固定讲解；
- V3 → V4：商品首次出现时间提前；
- V4 → V5：核心打法基本不变，仅场次答疑存在变化。

长期保留内容包括：

- 场次记录
- 场次演进关系
- 话术打法版本
- 打法版本演进关系
- 各场次归属的打法版本
- 开播和下播时间
- 相似度
- 变化摘要
- 关键策略
- 证据摘要
- 审核记录
- 是否采用
- 对正式话术产生的影响

长期研究的核心是同行直播打法如何从 V1 演进到 V2、V3、V4，而不是只保存逐字稿和相似度数字。

### 5. 最近两场与清理原则

每个同行重点保留最近两场完整直播的完整重素材。

部分录制场次在完成可用内容分析、证据提取和飞书回写后，也进入统一的重素材生命周期管理。除人工明确标记为长期保留的特殊场次外，不因“部分录制”身份而永久保留录像、音频或完整逐字稿等大文件。

当产生更新的完整场次，并且已经完成：

- 完整录制
- 完整转录
- 场次比较
- 变化记录
- 话术打法版本判断
- 策略提炼
- 飞书回写

更旧的完整竞品素材可以进入待清理状态。

待清理状态设置3天缓冲期。

缓冲期结束后可以清理：

- 旧录像
- 旧音频
- 旧完整逐字稿
- 不再需要的长文本镜像

不得删除对应的场次演进、话术打法版本、结构化历史数据、策略证据、审核记录和正式话术影响记录。

## 成功标准

做对了意味着：

1. 商品首次接入时，能够完整遍历当前权限范围内的同行列表并正确去重。
2. 首次扫描后仍会持续重新扫描商品，不会永久停止同行发现。
3. 新发现的同行能够自动进入飞书和监控范围，已有同行能够持续更新。
4. 同行身份与“商品 × 同行”带货关系被分别维护，不会相互覆盖。
5. 能够保留必要的商品带货关系及平台可见数据变化。
6. 同行开播后能够自动触发并尽可能完整录制。
7. 直播结束后能够自动生成带时间戳逐字稿。
8. 每场直播都有唯一且可追溯的场次记录。
9. 每个同行的新完整场次能够与上一完整场正确比较。
10. 能够区分固定讲解变化和答疑随机变化。
11. 能够清楚记录“哪里改了”，而不是只有一个总相似度。
12. 能够分别维护直播场次演进和话术打法版本演进。
13. 多个核心打法稳定的场次可以归属同一个话术打法版本。
14. 每个话术打法版本能够说明其起点、持续场次、核心内容、主要变化和当前状态。
15. 竞品策略能够追溯到真实同行、场次和时间戳。
16. 用户能够直接从飞书查看最近两场完整内容、分析、变化、建议并完成人工审核。
17. 历史重素材清理后，飞书仍能长期查看结构化历史、策略、审核结果及正式话术影响。
18. 未经人工批准不会修改正式知识库。
19. 批准后的修改生成新正式版本，并可追溯历史版本。
20. 每个同行只长期保留最近两场完整重素材。
21. 旧重素材严格执行完成条件和3天缓冲清理机制。
22. 飞书、Obsidian 和本地媒体仓库遵循明确的主数据源规则。
23. 竞品原始素材、候选策略和正式知识库保持清晰隔离。
24. 最终能够结合经过审核的知识生成新的原创直播话术。

## 做错了的判断标准

以下情况属于明显错误：

- 同行列表没有遍历完成却宣称完成。
- 第一次同行扫描完成后，永久停止该商品的同行发现。
- 新出现的同行没有进入飞书和监控范围。
- 商品、同行或直播场次关联错误。
- 同一个同行被大量重复创建。
- 把同行身份和商品带货关系混为同一数据对象。
- 用一个商品的带货数据覆盖同一同行与其他商品的关系数据。
- 直播未完整录制却标记为完整。
- 因最近两场相似而停止以后直播的完整录制。
- ASR 错误被直接当成确定事实。
- 逐字稿没有时间戳，无法返回原始证据。
- 只比较总相似度，不分析固定内容和商品承接。
- 把答疑不同误判成整体话术重大变化。
- 将每一个新直播场次都自动视为新的话术打法版本。
- 只保留场次和相似度，没有维护长期打法版本演进。
- 把单场临时表达直接判断为稳定长期策略。
- 竞品策略没有真实证据来源。
- 虚构销量、GMV、成交量或转化率。
- 用户必须进入 Obsidian 文件夹才能查看最近两场完整业务内容或完成审核。
- 未经用户批准修改正式话术。
- 将竞品原始素材直接写入正式知识库。
- 直接复制或洗稿同行逐字稿。
- 未完成转录、比较和飞书回写就清理旧素材。
- 未满3天缓冲期就自动删除重素材。
- 清理重素材时误删场次演进、打法版本、策略或审核记录。

## 人工兜底

以下情况需要人工介入：

- 巨量百应登录过期；
- 验证码或扫码验证；
- 平台风控；
- 账号权限异常；
- 页面结构异常导致无法可靠获取数据；
- 直播录制连续失败；
- 关键 ASR 内容无法确认；
- Agent 对竞品策略判断证据不足；
- 正式知识库变更的人工审批决策；
- 新话术准备投入真实直播。

人工处理完成后，Agent 应从最近的安全节点恢复，不得重复创建商品、同行或直播场次。

---

## 本期不做

- 不绕过巨量百应的登录、验证码和安全机制。
- 不获取当前账号无权查看的数据。
- 不虚构平台没有提供的数据。
- 不把 Agent 推断冒充真实事实。
- 不把竞品原始素材直接写入正式知识库。
- 不未经人工审核修改正式知识库。
- 不直接复制、洗稿同行内容。
- 不把所有大型直播视频上传到飞书。
- 不把全部长文本直接塞进多维表格单元格。
- 不因最近两场相似而停止后续完整录制。
- 不自动把生成的话术投入真实直播。

本岗位卡暂不规定：

- 商品同行重新扫描的具体频率；
- 商品与同行关系的具体存储结构；
- 话术打法版本的自动升级判定方式。

这些内容留到后续工作流和数据设计关卡确定。

## Agent 团队结构

### 主管岗位

**直播竞品情报主管**

负责：

- 接收和拆解商品任务
- 调度专业职责模块
- 检查执行状态
- 处理异常
- 汇总结果
- 发起人工审核
- 控制正式知识库写入

### 专业职责模块

| 职责模块 | 主要职责 |
|---|---|
| 同行发现 | 首次及持续扫描商品同行，维护同行集合和关系变化 |
| 飞书数据维护 | 新增、更新、去重、关系维护、状态和审核数据回写 |
| 开播监控录制 | 监控开播、创建场次、完整录制、检测下播和保存素材 |
| 直播转录 | 音频提取、带时间戳转录、清洗稿和低置信度标记 |
| 版本追踪 | 最新场次比较、打法版本归属和长期打法版本演进 |
| 竞品策略分析 | 将真实变化提炼为有证据的候选策略 |
| 话术优化 | 对比正式知识、生成 Diff、等待审核并在批准后创建新版本 |

这些是业务职责模块，不预先强制规定为多个独立 Agent。

后续拆工作流时，再根据任务是否需要自主判断、持续运行和独立状态，决定实现形态。

总体仍由“直播竞品情报主管”统一调度和控制。

## 核心业务闭环

### 主业务闭环

商品链接  
→ 首次完整发现同行  
→ 飞书去重并建立同行身份及商品带货关系  
→ 持续监控开播  
→ 建立场次并完整录制  
→ 自动转录与证据归档  
→ 最新两场场次比较  
→ 判断话术打法版本及其演进  
→ 提炼竞品策略候选  
→ 与正式知识库比较  
→ 生成话术修改 Diff  
→ 飞书人工审核  
→ 批准后更新正式知识库  
→ 生成新版原创直播话术  
→ 人工决定是否投入直播。

### 同行持续发现闭环

商品首次完整扫描  
→ 建立当前同行集合  
→ 后续周期性重新完整扫描  
→ 发现新增、存量更新和关系变化  
→ 新同行进入监控  
→ 更新飞书记录  
→ 等待下一次重新扫描。

具体扫描频率在后续工作流关卡确定。

### 持续监控与版本演进闭环

同行下一次开播  
→ 继续完整录制  
→ 形成新直播场次  
→ 与上一完整场比较  
→ 判断继续沿用现有打法版本或形成新版本  
→ 更新场次演进和打法版本演进  
→ 满足条件后清理过期重素材  
→ 永久保留结构化历史  
→ 等待下一次开播。

### 人工反馈闭环

用户采用、拒绝或纠正建议  
→ 保存审核意见  
→ 用于改进后续策略判断和建议排序  
→ 继续生成候选方案  
→ 仍须经过人工审核。
